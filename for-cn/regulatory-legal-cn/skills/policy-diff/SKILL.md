# /policy-diff

1. 读取 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` → 制度库索引。
2. 使用下文的工作流。
3. 从法规中抽取要求，与已索引制度匹配。
4. 输出：按要求逐条的差距分析，指明哪份制度需要更新。

## 事项上下文

**事项上下文。** 读执业级 CLAUDE.md 中 `## 事项工作区`。若 `启用` 为 `✗`（公司法务默认状态），跳过本段 —— 技能使用执业级上下文，事项机制不显现。若已启用且当前无活动事项，问：「本次工作属于哪个事项？运行 `/regulatory-legal-cn:matter-workspace switch <slug>`，或回答 `执业级`。」加载活动事项 `matter.md`。输出写入事项目录 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/matters/<matter-slug>/`。除非 `跨事项上下文` 为 `on`，绝不读取其他事项的文件。

## 目的

一条新规 / 修订刚发布。企业有既有制度。本技能找出**这条新规影响到哪些制度**，以及**「新规现在要求什么」和「制度现在写什么」之间的差距**。

## 加载上下文

`~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` → 制度库索引（制度、路径、责任人 / 责任部门）。

## 范围完整性

若用户要求把某个制度条目、某类要求、或某个类别从 diff 中排除：

1. 照做 —— 范围归用户所有。
2. **但要标记，且醒目、贯穿始终**：「⚠️ 范围限制：应用户要求排除 [X] 章节。本 diff **不反映**完整合规情况。被排除区域内的缺口**未识别**。」标记置于头部之上，向下游任何工件承载。
3. 把该标记同步交给 `gap-surfacer`：「本 diff 有范围限制。不得作为完整合规画面呈现。」在从本 diff 派生的所有缺口条目上原样带上范围限制标记。
4. 提示排除的**含义**：「排除『供应商管理』这一项意味着 diff 会显示『没有制度覆盖供应商管理』—— 这比暴露缺口更糟糕。」

在有隐藏范围限制的合规工件，在监管检查或诉讼开示中会被视为**掩盖**。标记是「我们缩了范围」和「我们把问题藏起来了」的区别。

## 工作流

### Step 0：diff 之前先确认法规现行有效性

在把一条法规对比制度之前，先确认该法规**现在正生效**。以下红旗表明该法规可能已不生效：

- 施行日 / 生效日已过 30 日以上但没有确认它未被延期
- 该法规发布已超过 12 个月
- 该法规是行政法规 / 部门规章草案的正式稿，可能被撤回或修订（中国实务中：修订、废止、被上位法覆盖）

出现红旗时，通过研究 MCP、网络检索（如已启用）、或国家法律法规数据库（`flk.npc.gov.cn`）核验：是否被修订、废止、被新规覆盖、被司法解释调整、被上位法优先。若能确认现行有效，继续。若不能确认，**在头部之上、任何内容之前**发出此横幅：

> `⚠️ 法规现行有效性未核实 —— 我无法确认该法规当前生效。正式发布的规章仍可能被修订、废止、被上位法优先。在你到国家法律法规数据库确认或与外部律师会签前，请勿将下文任何截止日视为具有约束力。`

在输出中把每个到期日标为：`[按公布内容 —— 现行有效性未核实]`。

法规现行有效性不确定性向下游传递。把缺口交给 `gap-surfacer` 时，标 `status_verified: false`，使其永远不会仅凭一纸公布日期就被扔进「已逾期」桶。

**中国法特别注意：** 中国立法体系存在效力层级 —— **法律 > 行政法规 > 部门规章 > 规范性文件 / 地方性法规**。在做 diff 之前先判断该文件的层级：

- 「法律」（全国人大 / 常委会通过）—— 最高效力
- 「条例 / 决定」（国务院制定的行政法规）—— 次于法律
- 「办法 / 规定 / 决定」（部委或省级人大制定的部门规章 / 地方性法规）—— 次于行政法规
- 「通知 / 意见 / 指引 / 公告」（部委或地方发的规范性文件）—— **通常不是强制性法源**，但监管检查时会作为尺度

在 diff 输出中标注文件层级，方便责任人判断合规必要性。规范性文件多数属于「参考执行」性质，不构成硬性合规义务，但监管认可度高。

### Step 1：抽取新要求

**不做静默补足。** 若给到的法规原文残缺或语义模糊，且已索引来源里没有完整版本 —— 停下并询问。**不要**从网络检索或模型知识里默默补齐。说：「我目前只有 [已有内容]。要准确抽取要求，还需要 [缺失部分]。选项：（1）粘贴完整原文；（2）指向一级源（国家法律法规数据库、发布机关公告页）；（3）从网络检索 —— 结果会被标 `[网页 —— 待核验]`，据以行动前请对照发布机关核验；（4）在这里停下。」由律师决定是否接受较低置信度的源；Claude 不代替律师做这个决定。

**来源标注。** 每条引用（法规文号、交叉引用、制度摘录）都要标注来源：
- `[国家法律法规数据库]` —— 从一级源取得
- `[发布机关官网 —— 网信办 / 市监总局 / 工信部 等]` —— 从发布机关一级源取得
- `[北大法宝 / 威科先行]` —— 从付费专业数据库取得
- `[网页 —— 待核验]` —— 网络检索取得
- `[模型知识 —— 待核验]` —— 模型训练数据回忆
- `[用户提供]` —— 用户直接粘贴

带 `待核验` 的条目 fabrication 风险更高，先核验。**输出中不得剥离或合并这些标签。**

读完这条新规，列出每条独立的新要求 / 修订要求：

| # | 要求 | 生效日 | 依据（法条 / 章节 / 条款） |
|---|---|---|---|
| 1 | [要求什么] | [日期] | [章节] |

要具体。「增强的信息披露要求」不是要求。「须在 [某流程] 中的 [某节点] 以 [某形式] 披露 [某内容]」才是要求。

### Step 2：映射到企业内部制度

对每条要求，最接近的**已索引制度**是哪一份？

- **直接命中：** 该制度显式覆盖该主题
- **间接命中：** 该制度覆盖相关主题，但这是一个新的子问题
- **无匹配：** 无制度涉及此点 —— 缺口是「制度不存在」

### Step 3：Diff

对每条直接 / 间接命中，读取该制度，做比对：

```markdown
### 要求 [N]：[名称]

**新规要求：** [具体要求]

**我方 [制度名]（末次更新 [日期]）现行规定：**
> 「[相关摘录]」

**差距：** [无 —— 制度已覆盖 | 部分 —— 制度涉及 X 但未涉及 Y | 完全 —— 制度与要求相矛盾或完全未涉及]

**需要的改动：** [具体 —— 例如「在第 3.2 条后增加一段关于 X 的规定」而不是「更新该制度」]

**制度所有者 / 责任部门：** [取自索引]
```

### Step 4：无匹配的缺口

无制度可对应的要求，单列一节：

```markdown
### 需新建制度

要求 [N]：[要求]

无现行制度涵盖。选项：
- 新起草一份制度（建议责任人：[覆盖最接近主题的团队 / 部门]）
- 加入现有 [关联制度] 作为新章节
- 判断本项不需要设专门制度（一次性合规义务，非持续性）
```

## 按输入类型分支

### 草案分支（征求意见稿 / 意见征求通知）

若输入是**征求意见稿**（尚未定稿，无强制要求），**不要**跑完整的缺口关闭 diff。改为产出一份**前置站位分析**：

- 指出一旦正式稿发布，**可能**需要变更的制度（不是今天要变）
- 判定草案涉及的问题领域是否与本公司实务相交，是否构成提交意见的价值点
- 记录意见截止日与档案中的**意见决策责任人**（取自 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md`）
- **不要**为草案逐条产出「无缺口」行 —— 草案不存在需要 diff 的强制要求。产出一段话，指出未来暴露与可能触及的制度即可

### 无差距分支（正式稿 / 草案 diff 到了错误的目标制度）

若抽取的要求全部对目标制度显示为「无缺口」，**不要**产出完整的逐条分析 —— 压缩为一段话：

```markdown
## 制度差异分析：[法规名称] —— [制度名称]

[法规名称] 看起来不会对 [制度名称] 提出改动要求。[制度名称] 第 [X] 条已经覆盖 [Y]。
本条法规实际影响到的可能是 [其他制度 1] 与 [其他制度 2] —— 请对这些制度重新运行
`/regulatory-legal-cn:policy-diff`。

复核时机：[下一次年度制度复核 / 触发事件 —— 例如「该法规被修订或有司法解释出台时」]。
```

一段话、一条建议、一条路由说明。不要为每条要求重复「无缺口」的结论 —— 汇总表已经承担了这个功能。对错误目标制度的无差距 diff，是**路由问题**，不是合规分析问题。

### 差距分支（正式稿 / 草案 diff 到目标制度且至少发现一条差距）

按下文规范做完整的逐条差距分析。详细 diff 格式适用于**真正发现差距**的情形。

## 输出


## 档案缺失时的回退

本技能从 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` 读取制度库索引。当索引为空或仍为 `[待填写]`：

- **制度库为空：** 默认把每条要求标为「无制度匹配」，输出追加：「你档案中的制度库为空，因此每条要求都被标为需新建制度。若你实际上已有制度涵盖这些要求，请通过 `/regulatory-legal-cn:cold-start-interview --redo` 或直接编辑 CLAUDE.md 补入，然后重新运行 diff。」
- **命中制度但未标注责任人：** 汇总表中「责任人」列留空，输出追加：「[列表] 的制度未标注责任人。请通过 `/regulatory-legal-cn:cold-start-interview --redo` 或直接编辑 CLAUDE.md 的制度库索引指派责任人，以便 gap-surfacer 可以路由。」

值已填写时不要提配置。

## 跨法域识别

本 diff 面向中国法。若法规是外国法或跨境规则（GDPR、CCPA、SEC、SOX 等），或制度库中某份制度明确适用外国法：

- 在头部之上给出跨法域说明：「本 diff 涉及外国法 / 跨境规则。中国境内的合规义务需并行判断（个保法、数据安全法、反垄断法等强制性规定不因约定外国法而豁免）。」
- 不要用中国法结构去分析外国法要求（例如把 GDPR「数据主体权利」直接映射到个保法权利体系而忽略两者差异），保持各自法域概念，并在末尾提示需外部律师会签。

## 交接

给 gap-surfacer：每一条部分 / 完全差距成为一条被跟踪的缺口，附责任人与截止日。

## 以下一步决策树收尾

按 CLAUDE.md `## 输出` 的规范结尾。把默认五个分支（起草 X、升级、补事实、观察等待、其他）调整为本次输出实际产生的内容。决策树是输出 —— 律师做选择。

## 本技能不做的事

- 不起草制度修订稿。本技能识别「哪里需要改」；制度改稿走 `/regulatory-legal-cn:policy-redraft` 或人工。
- 不对模糊监管文本做终结性解读。若某条规定可有两种解读，明确指出并交由律师判断。

## 转换决策自检

- **分级：** B 大改 —— 保留 diff 的整体架构（rule-status check → 抽取要求 → 映射制度 → 分支处理 → 输出），实体层大幅重写。
- **主要变化：** 新增中国立法体系效力层级（法律 / 行政法规 / 部门规章 / 规范性文件）意识；引文来源标签改为国家法律法规数据库 / 发布机关官网 / 北大法宝 / 威科先行；ANPR / RFI 换为「征求意见稿」；跨法域识别改为「外国法 / 跨境规则并行判断」。
