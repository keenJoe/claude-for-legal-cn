# /matter-update

1. 按下方工作流。
2. 确认 slug 在 `~/.claude/plugins/config/claude-for-legal-cn/litigation-legal-cn/matters/` 和 `_log.yaml` 中存在。
3. 询问事件类型、日期（默认今日）、摘要、字段变更（风险、状态、下一个期限、重要性重分类）。
4. 追加带日期的条目到 `history.md`。
5. 更新 `_log.yaml` —— 设 `last_updated: [今日]`，应用字段变更。
6. 确认。

# 案件更新

## 目的

组合只有保持时效才有用。本 skill 让记录更新变廉价 —— 两分钟结构化捕捉，避免自由发挥的漂移。

## 加载上下文

- `_log.yaml` —— 找到行
- `history.md` —— 追加目标
- `matter.md` —— 参照，不改写
- `CLAUDE.md` —— 若在重新评估风险则读风险分级

**利益冲突门槛 —— 不可绕过。** 更新前检查 `_log.yaml`。若无：

> "在案件台账中没找到 [slug]。先运行 `/litigation-legal-cn:matter-intake` —— 利益冲突检查是这一门槛，未做过立案检查的案件不能追加历史，也没有 `history.md` 可追加。"

## 输入

slug（必需）。若未提供，问 —— 附近期更新的案件短列表供选。

## 更新

### 1. 事件类型

- **程序性** —— 立案 / 收到起诉状 / 提交管辖异议 / 移送裁定 / 举证期限届满 / 开庭排期 / 开庭 / 调解 / 判决送达 / 上诉 / 二审开庭 / 二审判决
- **证据/取证** —— 证据固定完成 / 公证书出具 / 鉴定申请 / 鉴定意见收到 / 证人书面证言 / 证人出庭 / 调取证据申请
- **实体性** —— 新事实浮出 / 关键证据发现 / 对方新主张 / 己方策略调整
- **策略** —— 立场变化、和解要约提出/收到、和解授权更新
- **风险重评估** —— 严重程度或可能性变化
- **相关方** —— 新人拉入、外聘律师变更
- **行政/财务** —— 委托代理协议签署、预算调整、保全担保变更
- **保全/执行** —— 财产保全查封/冻结、保全解除、行为保全裁定、执行申请、执行到位、终结本次执行

或者当以上都不适用时自由描述。

### 2. 日期

默认今日。可覆盖（例如捕捉上周发生的事件）。

### 3. 摘要

一段叙事。发生了什么、意味着什么、任何即时含义。

### 4. 台账字段变更

按事件类型可能影响的字段逐项走：

- `status:` —— 阶段变了吗（立案 → 一审举证 → 一审审理 → 判决 → 上诉 → 二审）？
- `stage:` —— 子阶段
- `risk:` —— 是否需要重评估？
- `materiality:` —— 是否变化（新事实可能触发准备金/披露）？
- `exposure_range:` —— 若有新信息，调整
- `next_deadline:` —— 新的即将到来的日期
- `sol_deadline:` —— 诉讼时效日期变化（发律师函中断 → 重新起算）
- `outside_counsel:` —— 变更？
- `internal_owners:` —— 新增或移除？
- `evidence_preservation:` —— 证据保全更新/扩展/解除？
- `court:` / `case_number:` —— 立案后确认，或移送后变化

只提问受事件类型影响的字段。程序性更新通常只碰 `stage` 和 `next_deadline`；和解要约可能碰 `materiality`、`exposure_range`、`status`。

### 4pre. 和解授权关卡

若策略更新是**和解接受**（公司接受和解要约、签署和解协议、授权原则性接受 —— 不仅是记录发起或收到要约）：读 `## 谁在用这份档案`。若审查人是非律师：

> 接受和解有法律后果 —— 它解决权利主张，通常伴随撤诉/免除条款，且可能影响保险、税务、关联事项。你与律师确认过了吗？确认过就继续。若没有：一页纸沟通材料在此：
>
> [生成一页摘要：案件、拟和解条款（金额、结构、免除范围、保密、非贬损）、争议敞口、和解授权链路（CLAUDE.md `## 升级路径`）、可能出问题的地方、要问律师什么]

未获明确 yes 前，不基于接受和解的判断记录接受或翻转 materiality。记录发起或收到要约不触发此关卡 —— 接受才触发。

### 4a. 重要性再评估触发 —— 明确询问

以下事件类型强制触发重要性重检 —— **务必明确询问**，不允许沉默通过：

| 事件类型 | 重要性触发提示 |
|---|---|
| 实体性（新事实、关键证据、法院观点变化） | "这条是实体性事件。是否影响 `materiality`？当前：`[值]`。选项：`已提准备金 / 需披露 / 监控 / 无`。要改吗？" |
| 策略（立场变化、和解要约） | "和解活动常触发重要性重分类。当前：`[值]`。若要约、反要约、接受改变敞口或从有争议变为"很可能且可估计"，重新分类。" |
| 风险重评估（严重程度或可能性变化） | "风险移动了。重要性应跟随。当前：`[值]`。要重新分类吗？" |
| 监管/行政发展 | "监管动作（协助调查通知、行政处罚决定、执法立案）通常触发披露分析。当前：`[值]`。要改吗？" |
| 判决生效或执行到位 | "判决生效/执行到位应固定为已实现敞口，触发准备金减少或最终确认。当前：`[值]`。要改吗？" |

可接受回答含"无变化" —— 但"无变化"必须显式，不允许沉默视为无变化。历史条目捕捉：

```markdown
**重要性重检：** [无变化 / 从 X 改为 Y]
**理由：** [一句话]
```

若重要性移到 `已提准备金` 或 `需披露`，且案件之前没有准备金/披露，标注事件需通知财务/审计委员会（按 `CLAUDE.md` 重要性阈值）。

### 5. 关联文书提示（可选）

若更新涉及某文书（裁定、判决、往来函件），问是否有路径可链接。别追问。

## 写入

### 追加到 `history.md`

最新在上，紧接头部 `---` 之下。

```markdown
## [YYYY-MM-DD] —— [事件类型]：[短标题]

[段落摘要。]

**字段变更：**
- [字段]：[旧值 → 新值]
- [字段]：[旧值 → 新值]

**关联文书：** [路径，若有]
```

无字段变更时省略"字段变更"块。

### 更新 `_log.yaml`

- 应用字段变更。
- 设 `last_updated: [今日]`（或用户覆盖的事件日期 —— 台账追踪最后一次触碰记录的时间）。

## 确认

写入前把历史条目和 yaml diff 展示给用户：

> 我将追加这条，并更新台账。可以提交吗？

## 转换决策

- 分级：**A 直接转化**。工作流保留（结构化捕捉 → 字段更新 → 提交）；事件类型清单换为中国诉讼实务（立案、管辖异议、举证期限、开庭、调解、判决、上诉、二审、执行等）；添加保全/执行专属事件类型（原版没有单独列，中国实务保全和执行流程独立且频繁）；添加诉讼时效字段变更（原版无 `sol_deadline`，中国民法典 3 年时效需专门追踪）；和解授权关卡保留（对应中国实务的和解协议签署审批链）。

## 这个 skill 不做的事

- 编辑历史条目。修正是新条目引用并纠正旧的。
- 悄悄改台账。每次字段变更写入前展示给用户。
- 决定新进展是否需要准备金/披露。抛出问题（"这个可能推动重要性 —— 要重新分类吗？"），用户作答。
