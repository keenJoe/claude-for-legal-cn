# /policy-monitor

**扫描模式**（无参数或 `--sweep`）：
1. 读 `~/.claude/plugins/config/claude-for-legal-cn/privacy-legal-cn/CLAUDE.md` → 输出目录路径、政策文档、上次扫描日期。
2. 按下方流程执行。扫输出目录里自上次扫描以来的文件。
3. 逐份输出：提取被批准的实践 → 与当前政策承诺差分。
4. 归类差距：**必要**（政策与当前实践不符）vs **建议**（政策沉默）。
5. 逐差距：引当前政策原文、描述差距、起草建议措辞。
6. 更新 CLAUDE.md 里的「上次政策扫描」日期。

**直接查询模式**（附一段描述参数）：
1. 读 CLAUDE.md → 当前政策承诺 + 实际政策文档。
2. 解析拟议实践。与政策差分：数据类别、目的、第三方、保存期限、用户权利、告知。
3. 输出：覆盖 / 缺失 / 冲突 + 每个差距的建议措辞 + 时机建议。

**排程：** 在自己的日程工具里设一个每周提醒运行 `/privacy-legal-cn:policy-monitor`。排程执行需定时任务集成，本插件未捆绑。

```
/privacy-legal-cn:policy-monitor
/privacy-legal-cn:policy-monitor "我们想开始用行为数据个性化新用户引导邮件"
```

# 隐私政策监控

## 目的

隐私政策与实践漂移只朝一个方向：实践往前，政策落后。一份 PIIA 批了新数据类别。一份委托处理协议签了一个没在任何地方列过的受托人。分流结果给一个新用例批了「附条件」并要求一项政策还未做出的告知。几个月后有人读政策，与实际发生的不符。

本技能在漂移变成问题前抓住——要么每周爬输出目录，要么回答直接问题：「我们要开始做 X，对政策意味着什么？」

输出永远是：这里是差距，这里是建议措辞。

## 加载当前状态

读 `~/.claude/plugins/config/claude-for-legal-cn/privacy-legal-cn/CLAUDE.md`：
- `## 我们是谁 → 监管足迹` —— 在范围内的规则（个保法 / 数安法 / 网安法 / 行业专门规定）
- `## 隐私政策承诺` —— 从已发布政策提取的承诺
- `## 输出` —— 输出目录路径、政策文档位置、上次扫描日期

`## 输出` 含 `[待填写]` 时：
> 「输出还没配置。我可以跑直接查询检查——描述你计划做什么,我把它与你当前政策差分。要启用爬取扫描，先运行 `/privacy-legal-cn:cold-start-interview` 并提供输出目录路径。」

从 `## 输出 → 隐私政策文档` 里读实际政策文档。配置 CLAUDE.md 里的承诺是摘要，实际文档才是建议修订所依据的权威。

### 隐私承诺不只一面——都扫

网站隐私政策是一面。中国监管场景里，同一处理者的公开承诺通常还落在以下面上，且监管会检查它们之间的一致性：

1. **Cookie / SDK 同意管理平台 / 首启同意弹窗。** 同意管理平台承诺具体的 Cookie / SDK 类别与目的。若隐私政策说「使用分析类 SDK」而弹窗只提供「必要类」，冲突。网信办与工信部通报里，同意弹窗错配和 SDK 未申报是高频问题。
2. **应用商店隐私政策页 + 权限清单。** App 上架时提交的隐私政策与权限清单是自我声明,也受工信部/网信办通报。政策更新了而应用商店版没更新即是可见不一致。查：上次更新是何时？与当前政策的数据类别、目的、共享匹配吗？
3. **产品内同意流程。** 用户实际做出数据使用选择的界面（注册同意、设置开关、「政策已更新」对话）。政策说做什么;同意流程说用户同意了什么。二者应一致。
4. **行业专门告知。** 金融业「金融消费者权益保护」告知、医疗健康告知、征信告知、儿童个人信息处理规则。有自己的更新义务和与一般政策的一致性要求。

**在执业档案里为每一面加字段（位置 + 上次更新日期）。** 扫描逐面对比当前政策并标出发散：「隐私政策上次更新 [日期]。应用商店版上次更新 [更早日期]——可能未反映新数据类别。同意管理平台上次配置 [日期]——核实 SDK 清单与政策匹配。」

一份干净的隐私政策 + 一份陈旧的应用商店版 = 一起等着发生的工信部通报。**扫面而不是只扫文档。**

### 行业专门告知在扫描范围内

若 `## 监管足迹` 含以下任一，除网站政策外，扫描逐份对应告知差分——若没配置对应告知就标一个持续差距：

| 足迹条目 | 对应告知 | 标什么 |
|---|---|---|
| **金融业务**（金融消费者权益保护、征信业务） | 金融消费者告知 / 征信告知 | 输出暗示新数据类别、共享给非关联方、opt-out 机制变化而告知未反映 |
| **医疗健康、互联网诊疗** | 医疗健康数据处理告知 / 患者知情同意 | 输出暗示新使用或披露、新常规类别、患者权利机制变化未反映 |
| **不满 14 周岁未成年人** | 儿童个人信息处理规则（《儿童个人信息网络保护规定》第 8 条要求专门规则） | 输出暗示新儿童数据类别、新第三方披露、监护人同意机制变化 |
| **App / SDK 收集** | 应用商店隐私政策、SDK 清单、首启同意弹窗 | 处理活动与已声明清单不一致 |
| **汽车、地图 / 测绘等重要数据** | 汽车数据处理告知 / 测绘规则 | 触及重要数据认定但未做告知 / 本地化不一致 |

**若某个足迹里的规则未配置对应告知**，把这列为每次扫描的常态差距，不是一次性发现。扫描输出应含：

> **行业告知覆盖：**
> - [规则]：[已配置告知路径 + 上次更新，或「未配置——每次扫描持续标出直至解决」]

**若扫不到对应告知**明说——不要静默默认只对网站政策差分。一个依靠 policy-monitor 但静默忽略儿童告知的儿童教育 App 会带着过期的对外告知上线且无警示。把差距大声浮现出来。

**若足迹模糊就问用户。** 若 `## 监管足迹` 写「个保法 / 网安法」但输出扫描浮出金融账户、医疗健康、儿童数据类别，浮现足迹与实际实践的错位再继续：「你的足迹没列 [金融监管 / 卫健委规则 / 儿童条例]，但本次扫描看的输出涉及 [类别]。这个规则应加入足迹吗？有对应的告知要差分吗？」

## 模式 1：扫描

### 定范围

读 `## 输出 → 上次政策扫描` 日期。扫输出目录里晚于该日的文件。若无日期，扫全部并注明：「首次扫描——扫描全部输出。」

若输出目录为空或自上次扫描无新文件：
> 「自 [上次扫描日期] 以来无新输出。政策看起来与近期实践同步。下次排程扫描：[日期]。」

完成扫描后，把 `~/.claude/plugins/config/claude-for-legal-cn/privacy-legal-cn/CLAUDE.md` 的 `上次政策扫描` 更新为今天。

### 各输出类型看什么

**PIIA（个人信息保护影响评估）：**
- 提取：处理的数据类别、目的、涉及的第三方 / 受托人、保存期限、用户权利涵义、任何附加条件
- 标出：清单里不出现在当前政策承诺中的项

**委托处理协议审查（已签或已批）：**
- 提取：新增的受托人、已同意的数据位置、覆盖的处理目的、协议条款为个人创设的义务
- 标出：政策未列的受托人（若政策列名）、新处理类别、新数据位置、与政策不一致的义务

**分流结果（需做 PIIA / 可进行）：**
- 提取：什么被批准、任何隐含公开承诺的附加条件（如「上线前须告知受影响个人」）
- 标出：政策未覆盖的被批准实践、需要政策语言的条件

**权利请求答复：**
- 提取：本次答复浮出的、既往答复未见的新数据类别、加入系统清单的新系统
- 标出：政策未声明但实际收集的数据类别

### 差距识别

对每个标出的条目评估：

**必要更新** —— 政策做出的承诺与本输出相矛盾，或处理正在发生而政策完全无覆盖。不更新构成实质误陈。

> 例：政策说「我们收集姓名、邮箱、支付信息」。一份 PIIA 批了收集定位数据。政策什么都没说定位。这是**必要**更新——你在收集没披露过的数据（个保法第 17 条告知义务）。

**建议更新** —— 政策沉默但不冲突。不更新处理仍能站得住,更新会更整洁。

> 例：政策说「可能与服务提供商共享数据」。一份委托处理协议签了新分析受托人。政策没点名但也没排除。若维护受托人清单则建议加入。

## 模式 2：直接查询

### 解析拟议实践

从用户描述里提取：
- 收集或处理什么数据？
- 目的是什么？
- 还涉及谁（受托人、伙伴、第三方）？
- 个人信息主体是谁？
- 有自动化决策吗？
- 需要什么新的对个人的告知？

描述模糊就问一个澄清问题再继续。别做长导入——这个模式要快。

### 政策差分

把拟议实践对照政策每个相关章节：

| 检查 | 当前政策说 | 拟议实践 | 判定 |
|---|---|---|---|
| 数据类别 | [政策列的] | [如有新类别] | 🟢 已覆盖 / 🟡 差距 / 🔴 冲突 |
| 目的 | [声明目的] | [新目的] | |
| 第三方 / 受托人 | [声明当事方] | [如有新当事方] | |
| 保存 | [保存承诺] | [隐含保存] | |
| 用户权利 | [提供的权利] | [任何新权利涵义] | |
| 告知 / 披露 | [告知条款说的] | [本实践要求什么] | |
| 是否涉出境 | [出境承诺] | [如涉出境] | |

## 建议措辞的质量标准

政策语言应：
- 匹配现有政策的语气与风格（起草前读实际文档，不只是配置 CLAUDE.md 摘要）
- 具体到有意义但不到常规变化就打破的程度（「协助我们运营业务的服务提供商」比每次列名每个供应商更耐用）
- 不做团队做不到的承诺（如别写「我们绝不共享定位数据」如果架构里定位数据实际流向分析受托人）
- 标出可能需要更宽的政策立场变化的地方，而不只是加一句

起草时始终说加到哪一节。若正确的节不存在，明说并建议新建。

## 用下一步决策树收尾

按 CLAUDE.md `## 输出` 用决策树收尾。定制到本技能刚产出的东西——五个默认分支是起点。

若扫描浮出超过约 10 项漂移发现，或用户提出：提供仪表盘（见 CLAUDE.md `## 输出 → 数据密集输出可提供仪表盘`）。按本次输出定制——按面（政策条款 / PIIA / 协议 / 分流）计数、按严重度计数、可排序的发现网格含来源产物与建议整改。

## 本 skill 不做的事

- 不自己更新政策——它起草建议语言并标出决策，人审阅并批准每一处变化。
- 不抓监管变化——那是 `reg-gap-analysis`。本技能盯内部实践漂移,不盯外部法律变化。
- 不强制输出被保存——若团队没把 PIIA 存到配置目录，扫描找不到。直接查询模式不依赖保存的输出。
- 不读邮件或群消息里的非正式决定——只读保存到配置目录的结构化输出。
