# /use-case-triage

1. 读取 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/CLAUDE.md`。确认登记册已填写 —— 若没有，停下并引到设置。
2. 用下方框架。用例含糊就先问清。
3. 登记册查找 → 红线检查 → 分级。
4. 输出：分级、理由、条件表（若附条件）、治理层级、跨插件移交。
5. 若用例不在登记册中，提议登记更新。

```

```

## 事项上下文

**事项上下文。** 查看执业档案里的 `## 事项工作区`。若 `启用` 为 `✗`（法务部用户的默认值），跳过本段其余内容 —— 技能使用执业级上下文，事项机制不可见。若已启用且没有活跃事项，问：「这个属于哪个事项？运行 `/ai-governance-legal-cn:matter-workspace switch <slug>` 或说 `执业级`。」加载活跃事项的 `matter.md`。输出写入 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/matters/<matter-slug>/`。除非 `跨事项上下文` 为 `on`，绝不读其它事项的文件。

## 目的

拦住那种在走廊里发生、开头是「我们能不能直接用 AI 做这个」的对话。从登记册给一个快速、校准过的回答 —— 如果答案是附条件的，把条件写具体、把下一步说明白。

分流技能是关口，不是终点。它的活是分级、标出所需项、路由。深活由 aia-generation 干。

## 先读 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/CLAUDE.md`

分流前，永远先读它。那里的用例登记册和红线是权威。通用的 AI 伦理推理，不能替代这家公司实际决定过的东西。

若 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/CLAUDE.md` 含 `[待填写]`，抛出这个提示：

> 我注意到你还没配置执业档案 —— 我就是靠它把用例登记册、红线、治理层级贴合到你的实践。
>
> **两个选择：**
> - 运行 `/ai-governance-legal-cn:cold-start-interview`（2 分钟）配置你的档案，然后我按**你的**实践分流。
> - 说 **「临时」**，我用通用默认值分流 —— 中国法框架、中等风险偏好、律师角色、无 playbook —— 并给每个输出打 `[临时 — 配置档案以获得贴合输出]` 标记，让你在投入前看看我怎么做。

### 临时模式

用户说「临时」时，用这些通用默认值正常分流：中等风险偏好、律师角色、中国法框架、无登记册（按一般 AI 治理原则分类，而非匹配已登记条目）。给审阅备注和每个结论块打 `[临时]` 标记。输出末尾附：

> 「刚才是按默认假设的通用运行。运行 `/ai-governance-legal-cn:cold-start-interview` 得到贴合**你的**实践的输出 —— 你的登记册、你的法域、你的风险偏好。2 分钟。」

**法域范围。** 分流适用为 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/CLAUDE.md` 监管足迹配置的登记册、红线和治理层级。AI 规则因法域差异巨大 —— 一个足迹下「已批准」的用例，在另一个足迹下可能是「附条件」或被禁止。若部署触及足迹外的法域（例如系统还面向境外用户、或数据要出境），提出来并重新分流，不要类推延伸。

## 分流流程

### 第 1 步：理解用例

分级前，确保你真的懂在提议什么。描述含糊就问：

- 「AI 到底在做什么 —— 生成内容、作决策、给推荐、还是自动化一个任务？」
- 「AI 作用于谁或什么 —— 员工、客户、第三方、还是只有内部数据？」
- 「有人在动作发生前复核 AI 输出吗，还是全自动？」
- 「用哪个供应商或工具？」
- 「这是纯内部，还是触及客户或其它外部方？」
- 「会生成对外发布的内容吗？」（决定是否触发 AIGC 标识义务与深度合成规定。）

别让「我们想用 AI 做 [含糊的事]」不经分流就过去。问到足够具体，能对照登记册和红线检查为止。

### 第 2 步：红线检查

先查 `~/.claude/plugins/config/claude-for-legal-cn/ai-governance-legal-cn/CLAUDE.md` 的红线。命中红线，分流就此结束 —— 不管怎么包装。

**无论登记册怎么写，都独立检查这些中国法硬禁止：**
- 生成、传播危害国家安全、社会稳定、暴力恐怖、民族仇恨、淫秽色情、虚假有害等违法信息（生成式AI办法第 4、5 条）
- 利用深度合成制作、复制、发布法律行政法规禁止的信息，或未经同意伪造他人形象/声音（深度合成规定）
- 利用算法实施影响网络舆论、规避监督、垄断和不正当竞争，或对未成年人诱导沉迷、诱导消费（算法推荐规定）
- 未经单独同意、以违反最小必要或合法性基础的方式处理人脸等敏感个人信息（个保法第 28、29 条；最高法人脸识别司法解释）
- 生成合成内容不添加标识，或删除、篡改、隐匿标识（AIGC 标识办法）

命中任一，标 **不批准**，引用依据，路由到治理团队的禁止场景流程。

### 第 3 步：登记册查找与分级

在登记册中搜索匹配或类似条目。然后分级为三档之一。

#### 已批准

用例落在已批准类别内，满足附带的所有条件。

```
## 用例分流：[用例名]

### 分级
✅ 已批准

### 理由
匹配登记册条目「[条目]」。满足附带条件。

### 下一步
[任何持续义务 —— 例如「保持人工复核」「面向公众内容须加 AIGC 标识」]
```

干净的已批准用例不写长报告。

#### 附条件

用例可以做，但要满足具体条件。

```
## 用例分流：[用例名]

### 分级
🟡 附条件批准

### 理由
[为什么落在附条件而非直接批准]

### 治理层级
[标准 / 升级 / 高级 —— 来自 CLAUDE.md]

### 落地条件
| 条件 | 依据 | 负责人 | 时限 |
|---|---|---|---|
| [如：保留人工复核环节] | [如：算法推荐规定 / 团队制度] | [PM] | [上线前] |
| [如：面向公众内容加显式+隐式 AIGC 标识] | AIGC 标识办法 `[待核验]` | | |
| [如：完成科技伦理审查] | 科技伦理审查办法 `[待核验]` | | |

### 跨插件移交
[见下方移交部分]
```

#### 不批准

用例命中红线，或落入登记册明确否决的类别，或存在无法通过条件缓解的中国法效力/合规风险。

```
## 用例分流：[用例名]

### 分级
🔴 不批准

### 理由
[后果先说，依据后说]

### 依据
[红线 / 登记册位置 / 法条]

### 如果仍想推进
[升级到谁；需要什么才可能改变结论]
```

### 第 4 步：治理层级与移交

**治理层级**（来自 CLAUDE.md `## 治理层级`）：标准 / 升级 / 高级。层级决定审批路径。

**跨插件移交** —— 显式标记，写清到那边要回答什么问题：
- **到隐私：** 涉及个人信息处理时：「并行运行 `/privacy-legal-cn:pia-generation [系统名]`（若已安装）—— 本分流不替代个人信息保护影响评估。敏感个人信息或自动化决策还须单独同意（个保法第 28、29、24 条）。」
- **到 aia-generation：** 属升级或高级层级时：「运行 `/ai-governance-legal-cn:aia-generation` 出正式合规影响评估。」
- **到 vendor-ai-review：** 涉及新的 AI 供应商时：「上线前对 [供应商] 运行 `/ai-governance-legal-cn:vendor-ai-review`。」
- **到 reg-gap-analysis：** 浮现新的监管义务（如需算法备案、深度合成备案）时，那个技能跟踪缺口。

### 第 5 步：登记册更新

若用例不在登记册中，提议一个条目供人工审阅后加入 —— 不自动写。展示拟加的行，问是否加入。

## 批量分流

用户传 `batch` 或一个清单时，先估规模。多于约 10 个用例，先 scope：「这是 [N] 个用例。我可以对全部做快速分级出一张表，或对其中 3-5 个做详细分流。要哪个？」

批量输出为表格：

| 用例 | 分级 | 治理层级 | 关键条件 | 移交 |
|---|---|---|---|---|
| [用例] | ✅/🟡/🔴 | 标准/升级/高级 | [一句话] | [有/无] |

然后展开任何非干净已批准的行。

## 边缘情况与失败模式

**「我们已经在做了」的分流：**
若是追溯分流 —— 用例已部署 —— 直说，并在从头分类前先在登记册搜已覆盖该部署的现有条目。追溯分流常暴露一个条件已与现行实务漂移的旧条目；更新它通常比加新行更对。
> 「这看起来是追溯分流。如果它已经在跑而没有评估，那是要留档的缺口，不是挥手放过的事。我先在登记册搜有没有覆盖这个部署的现有条目，再重新跑分流。分级如下：[正常分流]。若附条件，那些条件现在就该确认到位，不能假定。若登记册有旧条目且部署已漂移，正确的跟进是更新那个条目而非加新行。」

**「只是内部用」不改变分析：**
影响员工的内部 AI（初筛、监控、评估）常比面向客户的 AI 风险更高 —— 员工个人信息处理受个保法约束，招聘算法受就业促进法与算法推荐规定约束。若用户暗示内部范围降低了风险，指出来。

**「供应商说安全」：**
供应商陈述不替代你自己的影响评估。指出来：
> 「供应商的立场不替代你自己的评估 —— 尤其对升级或高级层级的任何东西。」

**「我们只是试点」：**
触及真实员工或客户数据的试点，不豁免分流或影响评估。用同样的分级；若条件包含影响评估，试点也该有。

## 收尾决策树

按 CLAUDE.md `## 输出` 的决策树收尾。选项针对本技能刚产出的东西定制 —— 五个默认分支（起草 X、升级、补事实、观察等待、其它）是起点，不是锁死。树就是输出；律师来选。

## 跨法域提示

本分流适用中国法框架。若用例涉及境外主体、面向境外用户、数据出境，或约定适用外国法，在输出中标注并说明本分流结论可能不适用。AI 监管在各法域差异极大 —— 例如欧盟AI法按风险分级并对高风险系统设合格评定，与中国按服务类型（生成式/算法推荐/深度合成）+ 备案/标识的路径完全不同。
