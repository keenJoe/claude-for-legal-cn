# /cold-start-interview

执行冷启动访谈。首次运行写入 `~/.claude/plugins/config/claude-for-legal-cn/legal-builder-hub-cn/CLAUDE.md`；后续 `--redo` 重新访谈，覆盖前先展示差异。

## 检查当前状态

读 `~/.claude/plugins/config/claude-for-legal-cn/legal-builder-hub-cn/CLAUDE.md`：

- **不存在** → 开始访谈。同时若 `~/.claude/plugins/cache/claude-for-legal-cn/legal-builder-hub-cn/<版本>/CLAUDE.md` 存在已填好的档案，先复制过来并告诉用户「已从旧缓存迁移」。
- **含 `<!-- SETUP PAUSED AT: -->`** → 问候并续接：「欢迎回来。上次停在 [章节]。之前的回答已保存。从停下的地方继续，还是重新开始？」
- **含 `[待填写]` 但无暂停注释** → 模板从未完成；从占位符处继续，或询问是否重来。
- **已填好（无占位符、无暂停注释）** → 问：「看起来已配置完成。要重新访谈吗？覆盖前我会先展示差异。」除非传了 `--redo` 或 `--check-integrations`。

`--check-integrations` 只重跑下面「连接了什么」的连接性检查，更新档案的 `## 可用集成` 表，不动其他部分。

## 检查共享公司档案

看 `~/.claude/plugins/config/claude-for-legal-cn/company-profile.md`：

- **存在：** 读它，展示一行确认：「你们是 [公司名]，[执业环境]，[行业]，注册于 [注册地]，经营足迹 [足迹]。对吗？（或说『更新』修改共享档案）」确认后跳过公司问题，直接进入本插件专项。
- **不存在：** 说明本插件很可能是用户装的第一个法律插件，走完开场与 fork 后再问公司问题并写入共享档案，然后继续本插件专项。写完后告诉用户：「已保存公司档案 —— 其它法律插件会读它并跳过这些重复问题。」

公司字段（写共享档案，**不重复问**）：执业环境、公司主体全称、行业、主营业务、规模、注册地、司法管辖足迹、常见相对方、监管机构、风险偏好、升级审批人。插件专项字段（每插件一份，不进共享档案）：这里的信任姿态、白名单模式、被监控仓库、更新偏好、时效性阈值、QA 严格度、部署环境（个人/所内/嵌入产品）、执业领域信号（用于推荐）。

## 目的

本插件是「应用市场」。冷启动访谈是**入门推荐引擎** —— 问你做什么、推荐一个初始包、安装你挑的。

与其他冷启动不同，这个很短。五个问题、一个推荐、结束。

## 安装范围检查

工作目录在某个项目内（非用户主目录）时，提示一次：

> **注意 —— 本插件可能是项目级安装，我只能读取 [当前目录] 里的文件。如果要从别处（下载、文档、桌面）读文件，建议改为用户级安装 —— 见 QUICKSTART。可以继续用项目级，但需要把文件移到这个目录。**

确认后再继续。工作目录**就是**用户主目录时，跳过此检查（不说话）。

## 快路径 / 全量路径

- **快路径（约 2 分钟）：** 只问角色 + 执业领域。其余写 `[DEFAULT]`。用默认白名单（restrictive、GitHub + gitee 起始清单）、默认时效性窗口（法规 6 月、程序 12 月、样式 24 月、未知 3 月）、默认更新偏好（通知，不自动应用）。结尾：「已配置完成。已用合理默认值配置白名单与更新节奏。随时运行 `/legal-builder-hub-cn:cold-start-interview --full` 做全量，或 `--redo <章节>` 只重做一部分。」
- **全量路径（约 15 分钟）：** 完整流程（下文）。

## 开场前必做

### 1. fork 前导（3-4 行，说完等回答）

> **`legal-builder-hub-cn` 用于发现、安装与管理社区贡献的法务技能。** 想要某个执业领域的工作流？直接安装对应 `legal-*-cn` 插件；跑 `/legal-builder-hub-cn:registry-browser` 看仓库里有什么。
>
> **2 分钟**：角色 + 执业领域，加上白名单模式、更新节奏、宽松默认许可清单的合理默认。**15 分钟**：匹配你实际执业的初始包、写入 `allowlist.yaml` 的可信来源政策（仓库、发布方、许可 —— 由部署环境种子决定）、更新通知偏好、行业/规模信号（供推荐使用）。
>
> 快还是全？（随时 `/legal-builder-hub-cn:cold-start-interview --full` 升级。）

### 2. 用户挑完之后：定位

在自己的语气里覆盖：

- **本插件维护什么：** 你的执业档案（可信来源、更新偏好、部署环境）、决定安装能否放行的 `allowlist.yaml`、以及安装日志。
- **本次配置在做什么：** 帮你发现、安装、评估社区法务技能 —— 由执业档案驱动的初始包 + 触碰你工作流前的设计质量检查。学习执业档案与更新偏好并写入插件每次都会读取的纯文本文件。以后随时改。
- **数据来源：** 配置从你的回答构建全新执业档案。不读个人 Claude 历史、其它对话或主目录 CLAUDE.md。若本对话早前有相关信息（如公司名、团队），会先问再纳入。除非你输入或批准，什么都不加入配置。

**为什么重要。** hub 的初始包推荐和 auto-updater 的过滤都读这份档案。通用档案得到通用初始包 —— 「合理有用但没匹配」。告诉 hub 你是什么样的律师、常做什么，就把「所有其他人构建过的技能」变成「匹配你工作的那一组」。

## 访谈节奏

- **假定答案已在某处。** 问的信息可能有现成文档时，请用户粘链接或文件，不要凭记忆重打。
- **需要打字回答时先说：** 「这个需要打字回答 —— 我等你。」在收到回答前不进下题。
- **允许跳过。** 「先跳过，我在档案里标记 —— 之后可用 `--redo` 补。」但跟踪跳过项。写档案与推荐初始包前提醒用户：「有 [N] 项被跳过，要现在补吗？初始包推荐质量取决于档案完整度。」
- **绝不静默留空。** 每个占位符都必须是用户明确同意的跳过。
- **每轮最多 2-3 个可回答的问题（含子项）。** 屏幕能装下即可；装不下即过多。
- **暂停与恢复。** 「随时说『暂停』我就保存进度。下次跑本命令会续接。」暂停时把部分配置写入档案，顶部注释 `<!-- SETUP PAUSED AT: [章节] — 运行 /legal-builder-hub-cn:cold-start-interview 继续 -->`，未答字段标 `[PENDING]`（区别于 `[待填写]`）。恢复时问候「欢迎回来。上次停在 [章节]。之前的回答已保存。从停下的地方继续，还是重新开始？」，**不重复问已答问题**。

**用户答的客观事实即时核验。** 用户答的条文号、金额、期限、日期、公司名等，能核验的先核验再写入档案。冲突时提出：「你说阈值是 X；我的理解是 Y —— 确认哪个写入档案？`[前提待核验]`」错误事实写入 CLAUDE.md 会传播到所有输出，在这里抓住是产品中最高杠杆的一刻。

## 访谈内容

### 开场

> 我帮你发现并安装社区法务技能 —— 别人构建并分享的东西。先问：你是什么样的律师？我会推荐一个起始包。

### 第 0 部分：谁在用、连接了什么

在执业档案之前的两个快问题。它们决定插件如何工作，不决定它能做什么。

#### 谁在用

> 日常谁会用这个插件？（这决定「角色」信号 —— 跨全部 12 个插件传递，安装的技能有「非律师模式」时读这里而不再重复问；hub 自己的 `recommend` 与 `qa` 输出也会为非律师读者做结构化调整。）
>
> 1. **律师或法律专业人员** —— 律师、法务、合规、律师助理
> 2. **有律师可咨询的非律师** —— 创始人、业务负责人、合同负责人、HR、采购
> 3. **无常规律师渠道的非律师**

选 **2 或 3** 时，说明一次：

> 本插件负责发现与安装技能。你装的技能会按你的角色设置自身护栏 —— 我把这里的答案传下去，其它插件就不再重复问。

选 **3** 时补充：

> 需要找律师的话：当地律师协会、法律援助机构（12348）、公共法律服务中心 —— 通常有免费或低价的首次咨询。小微企业可找当地法律诊所或所在地司法局。

#### 连接了什么

> 本插件可以用到的集成：Slack 或企业微信 / 钉钉 / 飞书（新技能与更新通知）。让我检查哪些已经配置 —— 配置了的功能就能用，没配置的回退到手动。

**检查实际连接，不是配置声明。** 列在 `.mcp.json` 里的连接只是「可用」，真正能响应的才是「已连接」。二者混淆会毁掉信任。对每个插件用到的连接器：

- 能测试（调用一个简单 MCP 工具如列表或搜索）：只有真实调用成功才标 `✓`。
- 无法测试：标 `⚪`「已配置未验证 —— 打开 MCP 设置确认」+ 一行确认方法。
- **绝不因 `.mcp.json` 里写了就标 `✓`。**

未连接的告诉用户怎么接。例子：「企业微信没连。在 Claude Code 里 `/mcp` 添加，或用 Slack MCP 替代。没接也能用 —— 新技能与更新通知会在下次运行 `/legal-builder-hub-cn:registry-browser` 或 `/legal-builder-hub-cn:auto-updater` 时浮现，而不是实时推送。」

用以下格式汇报：

> - ✓ [集成] —— 已连接（已测试）
> - ⚪ [集成] —— 已配置未验证。打开 MCP 设置确认。
> - ✗ [集成] —— 未找到。[功能] 将回退到 [手动方式]。[如何连接]

「不需要接。核心功能仅靠文件访问就能用 —— 浏览、安装、QA、更新。」

把第 0 部分答案写入插件档案的 `## 谁在用` 与 `## 可用集成`。本插件写 `## 谁在用`，让**其它安装的插件**从这里读角色而不再重复问。

### 第 0.5 部分：可信来源与部署环境（关卡关键）

在五个问题之前问：

> 你已经有一份社区技能仓库监控清单，或你们团队的可信来源 / 屏蔽来源白名单吗？可以粘内容、指路径，或说「没有，用默认」。你给的话我读进档案并加进 `allowlist.yaml`，就不用你重打。（这条给 `/legal-builder-hub-cn:skill-installer` 用 —— 安装器抓取前先读白名单，restrictive 模式下不在清单上的来源一律拒绝。）

**部署环境**（在白名单问题之后、写文件之前问）：

> 你打算怎么用装的这些技能 —— 只自己用、所内共享，还是嵌入你交付的产品或服务里？（个人 / 所内 / 嵌入产品。）这个决定 `allowlist.yaml` 的 `licenses:` 起始清单，`/legal-builder-hub-cn:skill-installer` 会拒绝任何不在清单上的许可证。
>
> - **个人：** 大多数开源许可都可以（MIT、Apache-2.0、BSD、ISC、CC0-1.0）。
> - **所内：** 上面加上文件级 copyleft（LGPL、MPL —— 你不对外分发时无碍）。
> - **嵌入产品：** 最严 —— 强 copyleft（GPL、AGPL）会产生需法律审查后才能发货的义务，被标记为需签字而不是默认允许。

把答案记入档案 `## 我信任的来源` 下的 `部署环境: [个人 | 所内 | 嵌入产品]`。下面 `licenses:` 起始清单从这里取。

**把白名单写到 `allowlist.yaml`，不只是档案里。** 安装器读 `~/.claude/plugins/config/claude-for-legal-cn/legal-builder-hub-cn/allowlist.yaml`，不读 CLAUDE.md。只写档案而不写 yaml，安装器看到空白名单会退回 permissive —— 头号结构性防线被无声消解。所以本步骤要：

1. 在配置路径下写 `allowlist.yaml`，schema 见 `skills/skill-installer/references/allowlist.md`：
   - `mode:` —— 默认 `restrictive`（失败关闭）。个人 / 小团队 提议 `permissive`（他们没有 IT 白名单，restrictive 会拒绝一切）；中大型 / 公司法务 / 政府默认 `restrictive`。**每次都确认**：「我把白名单模式设为 [模式]。Restrictive 在你加入前拒绝未知来源 —— 最安全，但每个新发布方都要批。Permissive 标记未知来源并问你 —— 更方便，不那么严。你要哪个？」**未经用户明确同意，绝不写 permissive。**
   - `registries:` —— 用户提供的 + 默认起始（`github.com/legalopsconsulting/lpm-skills`、若有 gitee 镜像也加入；国内技能市场经用户确认后加入）。
   - `publishers:` —— 用户命名的 GitHub / gitee 用户名或组织，或起始仓库的所有者。
   - `connectors:` —— 用户未提供时留空；restrictive 模式下提示：「Restrictive 模式需要连接器白名单 —— 粘经批准的 MCP 服务器 URL，或我留空，技能声明任何连接器都会被拒绝。」
   - `licenses:` —— 按上面部署环境种子填：
     - **个人** → `MIT`、`Apache-2.0`、`BSD-2-Clause`、`BSD-3-Clause`、`ISC`、`CC0-1.0`。
     - **所内** → 同「个人」加 `LGPL-2.1-only`、`LGPL-3.0-only`、`MPL-2.0`。
     - **嵌入产品** → 同「个人」。同时在 `allowlist.yaml` 顶部写注释：`## 发货前需法律审查许可证 —— 清单外的许可证需法律签字。` 强 copyleft（GPL、AGPL）故意不放默认；要加须显式编辑。
2. 也在档案 `## 我信任的来源` 里概括，方便人读到政策。
3. 告诉用户位置：「你的白名单在 `~/.claude/plugins/config/claude-for-legal-cn/legal-builder-hub-cn/allowlist.yaml`。安装器抓取前先读它。」

用户上传注册表 / 白名单文件时：读它，提取仓库 URL 与白名单/屏蔽项，确认发现，按 schema 写 `allowlist.yaml`，并在档案概括。

### 第 0.7 部分：时效性提醒

白名单问完（部署环境已定）、五个问题之前，问：

> 社区技能捆绑参考资料（法规、法条、程序模板）时，多久没核验就该提醒你再验一次？（法规内容常见默认 6 个月。程序 / 样式内容 12 个月。工作节奏快的领域可以更短。）

接受单个数字（对法规生效，其它类别用下面默认）或按类别分别答。校验每个答案形如 `N days`、`N months` 或 `N years`，N 是 1 到 120 的正整数 —— 拒绝自由散文，重新问。

写入档案 `## 时效性提醒`（放在 `## 我信任的来源` 之后、`## 已安装初始包` 之前）：

```markdown
## 时效性提醒

| 内容类别 | 提醒前最大年龄 | 依据 |
|---|---|---|
| regulatory（法规） | 6 个月 | 监管更新频繁；执法重点常变 |
| procedural（程序） | 12 个月 | 法院规则与程序变化较慢 |
| stylistic（样式） | 24 个月 | 内部风格、格式模板 |
| unknown（未声明） | 3 个月 | 未声明时效的技能保守处理 |

当技能的 `last_verified` + `freshness_window` 已过，或用户以上阈值已过 —— 取更严的 —— 时，skill-installer 在运行前浮现警告。
```

用户给了更严的数字就替换默认；说「用默认」就照上表写。

用户没上传注册表清单时，五个问题结束后提议：「要不要把你监控的仓库与更新偏好写成一份团队可分享的政策说明？内容和档案里的一样，格式化后可给同事或新构建者看你信任哪些来源、你想怎么处理更新。」

### 五个问题

1. **执业领域** —— 公司法务还是律所？商务、隐私、产品、劳动、诉讼、并购、其他？（供 `/legal-builder-hub-cn:related-skills-surfacer` 用 —— 执业领域是初始包的主键。）

   **不落入类别的执业。** 用户的执业不匹配上述选项（国际仲裁、国际公法、amicus-only、学术咨询、公益法律援助、涉军民融合、海事等）时提议：「听起来你的执业不落入我常用的类别。用你自己的话讲讲你在做什么、给谁、什么法域与场合、工作是什么样 —— 我从描述里构档，不硬塞进不合适的框。」按自由描述构档，标出哪些模板字段被填、被改造或空缺。硬套的档案比稀疏的档案更糟。

2. **行业** —— 互联网、医疗、金融、其他、无所谓？（供 `/legal-builder-hub-cn:related-skills-surfacer` 与 `/legal-builder-hub-cn:registry-browser` 用 —— 行业收窄初始包并过滤仓库结果。）

3. **团队规模** —— 单人、小团队（2-5）、大型法务部？（供 `allowlist.yaml` 模式默认使用 —— 单人 / 小团队默认 permissive，中大型 / 公司法务 / 政府默认 restrictive。）

4. **你最常做的事是什么？** —— 合同审查、合规、上线审查、并购支持、诉讼答辩起草等。（供 `/legal-builder-hub-cn:related-skills-surfacer` 用 —— 当你在做社区有相应技能的事情时，surfacer 会提示你。）

5. **工具熟悉度** —— 构建者（你自己写技能）、修补型（你改现有技能）、开箱即用型（你希望装了就能用）？（供 `/legal-builder-hub-cn:related-skills-surfacer` 用 —— 构建者拿到原始仓库与 `/legal-builder-hub-cn:skills-qa` 框架；开箱即用型拿到一个精心策展、能直接跑的包。）

### 推荐

把档案映射到仓库技能：

| 档案 | 初始包 |
|---|---|
| 公司法务、互联网 | commercial-legal-cn 插件 + lpm-skills 中的事项工作区/范围控制技能 |
| 隐私合规 | privacy-legal-cn 插件 + 社区 DPA/PIA 技能 |
| 产品法务 | product-legal-cn 插件 + 社区营销审查技能 |
| 律所诉讼 | litigation-legal-cn 插件 + lpm-skills 中的事项规划/预算技能 |
| 单人 / 小团队 | 全部轻量 —— 分流类技能优先于完整审查类技能 |
| 构建者 | 原始仓库 + skills-qa 框架 —— 他们自己构建和验证 |

对每个推荐的技能：展示 SKILL.md 描述。让他们挑 —— 没有明确 yes 不安装。

## 写执业档案

写 `~/.claude/plugins/config/claude-for-legal-cn/legal-builder-hub-cn/CLAUDE.md`（创建父目录）。结构用插件根目录 `CLAUDE.md` 模板为骨架。短。档案 + 已安装清单 + 白名单/时效性偏好。

结构（按模板章节）：**我们是谁 / 谁在用 / 可用集成 / 我信任的来源（含部署环境）/ 时效性提醒 / 已安装初始包 / 被监控仓库 / 更新偏好 / 输出（内含跨插件护栏，本 hub 自身不产法律工作成果，但要向所安装技能传递「非律师模式」信号）/ 主观法律判断立场 / 共同护栏 / 检索内容的可信度 / 跨法域识别 / 比例原则 / 大输入处理 / 已录入的样本文件**。

写入前重读访谈期间收到的任何文档（白名单文件、政策说明），不要凭对话记忆。

   > - **按设计框架评估一个技能** —— 例如「对一个技能跑法律技能设计框架 —— 十三项参数、三项失败模式、一次信任面检查，以及中国法语境核验。」试 `/legal-builder-hub-cn:skills-qa`

## 客观事实核验（写档案之前）

用户答的条文号、金额、期限、日期、公司名等，能核验的先核验再写入档案。冲突时先提出。错误事实写进档案会传播到所有输出。

## 失败模式（避免）

- **不写 YAML 样式的「配置文件」** —— 档案是可读散文 + 表格。
- **不跳过样本文件 / 白名单文件** —— 访谈提供「他们认为的政策」，文件提供「实际生效的政策」，两者都重要。
- **不写通用 playbook** —— 用户答「大致就好」时追问具体：「给我个数或名字。你说的仓库指哪一个？发布方叫什么？」
- **不承诺本插件没有的技能能力。**
- **不在每次会话都跑访谈** —— 先检查配置文件；填好了就结束。
- **一次不超过 2-3 个可回答的问题（含子项）。**
- **不承诺本 hub 有法律实务判断能力。** hub 不产法律工作成果 —— 它发现、安装、评估。实体法判断在所装插件里进行。

## 语气

热情、好奇、像做了功课的新同事。不说「请提供」—— 说「你们那个 X 是怎么处理的」。不说「配置您的设置」—— 说「告诉我你们团队怎么工作」。
