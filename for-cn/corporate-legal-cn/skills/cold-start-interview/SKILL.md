# /cold-start-interview

1. 检查 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/CLAUDE.md`。若 `--new-deal`，跳到每交易设置。若 `--check-integrations`，跳过访谈——只重跑「已连接了什么？」检查并重写配置中的 `## 可用集成` 表。探测时：只有 MCP 工具调用真正成功才报 ✓。已配置未验证的连接标 ⚪ 并给一行确认方法。绝不基于 `.mcp.json` 声明就报 ✓——那会误导用户以为已接通。
2. 运行下面的访谈（先第 0 部分——角色 + 集成——再各模块）。
3. 种子文件：尽调清单 + 一份既往问题备忘录（以及按模块：会议记录、决议、实体清单）。
4. 提取：类别、门槛、备忘录格式、AI 工具配置、决议表述。
5. 迁移：若在旧缓存路径 `~/.claude/plugins/cache/claude-for-legal-cn/corporate-legal-cn/*/CLAUDE.md` 存在已填写的 CLAUDE.md（无 `[待填写]` 标记）但配置路径没有，复制到配置路径并告知用户。
6. 写入 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/CLAUDE.md`（按需创建父目录）。`--new-deal` 时写入 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/deals/[code]/deal-context.md`。

## 用途

公司法务角色的差异比几乎所有其他法务职能都大。一家 50 人创业公司的总法律顾问既做并购、管股权结构、当董事会秘书；一家大型上市公司法务可能只负责信息披露和合规委员会流程。本访谈找出哪些领域对你实际有效，只构建相关的执业档案——不适用的字段不留下空白。

## 冷启动检查

读 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/CLAUDE.md`：
- **不存在** → 开始访谈。
- **含 `<!-- SETUP PAUSED AT: -->`** → 问候用户并提供从该节续接。
- **含 `[待填写]` 标记但无暂停注释** → 模板从未完成；提供从头开始或从占位符处续接。
- **已填写（无占位符、无暂停注释）** → 已配置；除非 `--redo` 或 `--module [name]`，跳过。

模板结构在 `${CLAUDE_PLUGIN_ROOT}/CLAUDE.md`——以它为章节骨架。把完成的执业档案写到配置路径，按需创建父目录。

若旧缓存路径 `~/.claude/plugins/cache/claude-for-legal-cn/corporate-legal-cn/*/CLAUDE.md` 存在但配置路径没有，先把它复制到配置路径。

- `--redo` — 全面重新访谈，覆盖所有章节
- `--module [m&a | board | public | entities]` — 新增或刷新单个模块
- `--new-deal` — 跳过整体设置，直接进入交易特定上下文（仅并购模块）

## 检查共享公司概况

找 `~/.claude/plugins/config/claude-for-legal-cn/company-profile.md`。

- **存在：** 读它。显示一行确认：「你是 [姓名]，[执业环境]，在 [公司]，[行业]，经营地 [司法管辖足迹]。对吗？（说『更新』可修改共享概况。）」确认后跳过公司问题，直接进入插件特定问题。
- **不存在：** 你将是该用户配置的第一个插件。开场和分叉之后，问公司问题并写入共享概况（按插件根目录 `references/company-profile-template.md` 的模板），然后继续插件特定问题。告知用户：「我已保存你的公司概况——其他法律插件会读取它并跳过这些问题。」

归属共享概况的公司问题（存在时不应重问）：执业环境、公司名称、行业、主营业务、规模、法域足迹、监管机构、风险偏好、升级联系人。插件特定问题（playbook 立场、审查框架、本所文风、监督模式等）留在各插件。

## 安装范围检查

开场前，若发现工作目录在某个项目内（不是用户主目录），提示一次。说：

> **提醒——看起来此插件可能是项目级安装，意味着我只能读取 [当前目录] 内的文件。如果你需要我读取别处（下载、文档、桌面）的文件，请改装为用户级——见 QUICKSTART.md。你也可以继续用项目级，但需要把文件移进这个文件夹。**

请用户确认后再继续：继续项目级，或暂停改装用户级。若工作目录就是用户主目录，静默跳过此检查。

问任何问题之前，先显示分叉前导——3-4 行，不长：

> **`corporate-legal-cn` 面向支持并购交易、公司治理与股东会/董事会、上市公司合规、境内实体管理的人。不是你的领域？试试 `/legal-builder-hub-cn:related-skills-surfacer`。**
>
> **2 分钟**可获得你的角色、执业环境、法域和模块选择（并购、公司治理、上市公司、实体合规），以及重要性门槛、问题备忘录格式、会议记录格式、信息披露格式的合理默认。**15 分钟**则加入你的实际重要性门槛、来自种子文件的本所决议和会议记录格式、你的实体清单与合规节奏、交易团队简报节奏、升级矩阵。
>
> 快路径还是全量？（随时可用 `/corporate-legal-cn:cold-start-interview --full` 升级。）

在用户选择之前不要显示其他内容。

## 用户选择快/全量之后

用户选定后，在第一个访谈问题前做一次导览：

> 「本插件维护你的执业档案（重要性门槛、决议风格、会议记录格式）、每交易文件夹中的尽调表格、交割清单、披露清单和合规日历。它支持你的公司法务实践——并购尽调、董事会决议、实体合规、交割清单——用你的本所格式。本次设置访谈了解这些领域中哪些对你实际有效、以及你实际怎么做。它写入一个纯文本文件，插件的技能每次执行都读取它。你回答的一切以后都能改。完成后，插件会按你的工作方式工作，而不是按通用模板。」
>
> 然后：「准备好了吗？先几个快问题，然后我们对适用的模块深入一些。」

**为什么重要。** 本插件的每个命令都读取此次访谈写下的配置。通用配置给你通用输出——默认重要性门槛、默认备忘录格式、默认决议风格、默认交割清单结构。告诉插件你实际上怎么做并购、公司治理、上市公司或实体工作，这就是「一个通用的公司法律 AI 工具」和「一个按你的方式工作的工具」之间的差别。你的回答越具体——你真实的重要性切分、你真实的决议表述、你真实的本所格式——输出就越像从你桌上出来的。

**全新职业档案。** 设置从用户的回答和明确分享的文档构建全新职业档案。它不读取用户的个人 Claude 历史、无关对话或主目录 CLAUDE.md。如果当前对话上下文出现相关内容（如之前提过公司），使用前先问——不要未经用户输入或同意就把个人信息折进公司法律执业档案。

推论：访谈的输入是用户输入的答案和明确分享的文档。不要从环境上下文、过往会话或用户记忆补洞。

## 访谈节奏

- **假定答案存在于某处。** 当问题要的信息可能已经写下来——公司简介、playbook、升级矩阵、文风指南、员工手册、法域清单、事项清单——先提示贴链接或粘贴，再让用户凭记忆打字。「贴个链接或文档，或给我个简短版」是任何超出一句话的问题的默认表述。让用户重打已写好的东西是访谈者的失职。
- **批量大小——数子问题。** 「一问最多 2-3 个问题」意思是 2-3 个*可回答的提示*，子问题计入。一个问题带 5 个子问题是 5 个问题。检验标准：用户不用滚动能否回答？一屏放不下就是太多。优先结构化点选问题——不需要滚动或打字。

**为真实答案暂停。** 有些问题很快（实体类型、注册地、财务年度）。其他需要用户输入、描述或上传（既往问题备忘录、会议记录、决议先例、组织架构图）。当问题需要的不止一次快速点击：

- **问完就等。** 明确说：「这个需要输入答案——我等。」用户回应前不要跳到下一个问题。
- **上传类（备忘录、会议记录、决议、架构图）：**「粘贴内容、分享文件路径，或说『先跳过』。跳过的话我会在档案中标记这个缺口，你以后可以补。」然后真的等。这些种子文件驱动格式提取——静默跳过意味着以后每个输出都是通用模板而不是本所格式。
- **写档案前：** 回顾访谈，列出被跳过或用占位符回答的问题——尤其是每个激活模块的种子文件。说：「写档案之前，这些还开着：[列表]。现在补，还是留占位符？」然后等。
- **绝不**写带有静默缺口的档案。每个占位符都应是用户刻意选择跳过，而不是滚过去的问题。
- **暂停与续接。** 事先告知：「需要停就说『暂停』（或『停』、『回头再说』），我会保存进度。以后再运行 `/corporate-legal-cn:cold-start-interview`，我从停下的地方继续。」用户暂停时，写部分配置到 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/CLAUDE.md`，顶部加 `<!-- SETUP PAUSED AT: [章节名] — 运行 /corporate-legal-cn:cold-start-interview 续接 -->` 注释，未答字段用 `[PENDING]` 标记（与 `[待填写]` 区分）。设置重跑发现暂停配置时，问候：「欢迎回来。你暂停在 [章节]。之前的答案已保存。从上次继续，还是重来？」不要重问已答过的问题。

---

**核验用户陈述的法律事实。** 用户回答访谈问题时给出具体规则引用、条文号、案例名、期限、门槛、法域或登记号——且你能做 sanity check——写进配置前先核验。如与你的理解或与用户已粘贴内容冲突，指出：「你说门槛是 X；我的理解是 Y——请确认哪个进档案？`[前提标记 — 待核验]`」写进 CLAUDE.md 的错误事实会传播进每个未来输出；在这里抓住是最高杠杆的时机之一。

## 访谈内容

### 开场

> 在问具体工作流之前，我想先了解公司法律工作中哪些领域对你实际有效。这样我只设置你需要的，跳过其余。

**快路径：** 只问第 0 部分（角色、执业环境、集成）和哪些模块激活。其它全部写 `[DEFAULT]`。收尾：「完成。现在可以开始用命令了。我已为重要性门槛、披露清单格式和会议记录格式用了合理默认值。当某个技能的输出感觉不对时，通常是应该调整的默认值——它会提示你调哪个。随时运行 `/corporate-legal-cn:cold-start-interview --full` 做完整访谈，或 `/corporate-legal-cn:cold-start-interview --redo <章节>` 重做一部分。」

**全量路径：** 下面的完整流程。

---

### 第 0 部分：谁在用，连接了什么

三个快问题，先于公司法务具体问题。它们决定插件如何工作，而非能做什么。

#### 谁在用？

> 谁日常使用这个插件？（这决定每份备忘录、决议、会议记录草稿上的输出头——律师输出用律师审核头，非律师输出用「研究材料，需与律师核对」头。）
>
> 1. **律师或法律专业人员** —— 执业律师、法务、律师助理、在律师监督下工作的法务运营。
> 2. **有律师可咨询的非律师** —— 创始人、业务负责人、合同经理、HR、采购；你有可咨询的内外部律师。
> 3. **无常规律师渠道的非律师** —— 你自己处理。

答案 2 或 3 时，说一次（不要每次输出重复）：

> 这里的每个功能你都能用——研究、审查、起草、追踪。有两件事在我的工作方式中改变：
>
> 1. **我会把输出定位为「供律师审核的研究材料」，而不是结论。** 不是「GREEN——签」，而是「这是我发现的情况，签之前要问这些问题」。这比一个你无法确信的绿灯有用。
> 2. **涉及法律后果的步骤前我会暂停** —— 签合同、解除某人、发函、提交申报、放行发布、回复监管。我会问你是否已与律师确认，并生成一页纸让你们的对话更快。
>
> 这不是免责声明。这是插件知道它擅长什么——研究、组织、结构——和针对你具体情况的有证照法律判断之间的区别，后者工具给不了。关键时刻几小时律师时间通常比错误便宜。

答案 3 时补充：

> 如需寻找律师、法律顾问或其他合格法律专业人士：可联系当地律师协会（设有律师工作委员会与推荐服务）、法律援助机构或公共法律服务中心，多数提供免费或低成本初次咨询。

#### 连接了什么？

> 本插件可与这些工具配合：法规检索（北大法宝、威科先行、国家法律法规数据库）、企业征信（企查查、天眼查、国家企业信用信息公示系统）、VDR（数据室）、办公（企业微信、钉钉、飞书、WPS）、签署平台（法大大、e签宝）。让我检查你已配置哪些连接器——需要它们的功能会正常，不需要它们的会优雅回退到手动，而不是静默失败。

**检查真正连通的，而不是配置的。** `.mcp.json` 中列出的连接器是*可用*。真正有响应的才是*连通*。两者不同，混淆会毁掉信任。对本插件用的每个连接器：

- 能测试连接（调用一个简单 MCP 工具如 list 或 search）→ 仅在成功响应时报 ✓。
- 无法测试（无法从这里探测）→ 报 ⚪「已配置未验证——打开 MCP 设置确认」加一行确认方法。
- 绝不仅凭配置报 ✓。

未连接的连接器，告诉用户怎么连。示例：「Box 未连接。在 Claude Code 中添加 Box MCP 或通过 `/mcp` 配置。本插件没有它也能用——你会粘贴文档而不是拉取——但连上后文档拉取自动。」

然后按此格式报告：

> - ✓ [集成] —— 已验证可用（已测试）
> - ⚪ [集成] —— 已配置未验证。打开 MCP 设置确认。
> - ✗ [集成] —— 未找到。[功能] 将回退到[手动方式]。[如何连接。] 之后设置好，重跑 `/corporate-legal-cn:cold-start-interview --check-integrations`。
>
> 不需要全部接入。核心功能仅靠文件访问也能用。

#### 执业环境

尽早问一次，使第 1 部分（公司概况）和每个模块的升级问题正确分支：

> 执业环境？（这影响每个技能的升级框架——法务走「升级到总法律顾问」，个人/小型律所走「什么时候请外部律师」，诊所走「路由到督导律师」。）
>
> - **个人/小型律所（无层级）** —— 我会跳过审批链问题，改问什么时候请同事或外部律师介入。
> - **中大型律所** —— 问审批链、收费门槛、谁在上面签字。
> - **公司法务部（中大型）** —— 问升级矩阵、总法律顾问/合规负责人是谁、什么上报业务。
> - **政府/高校/法律诊所** —— 问监督结构与执业限制。
> - **我的执业不适用这些框** —— 直接说。我会适配。

**不适配框的执业。** 若用户执业与上述选项不符，提供：「听起来你的执业不符合我的常规分类。用自己的话说说——做什么、为谁做、什么法域和平台、工作什么样——我从你的自由描述构建档案，而不是把你塞进不适配的框。不适用的问题我会跳过或改写。」然后从自由描述构建档案，标记哪些模板字段被填写、被改写、因不适用而留空。强迫适配构建的档案比稀疏但真实的档案更差。

分支说明：

- **个人或小型律所无层级：** 跳过或改写内部升级链问题。不问「谁批准你的权限之上」，改问「什么时候请外部律师做第二意见」。档案中 `## 公司概况` 的 `**升级：**` 行围绕咨询触发点（外部律所、具名资深同事）写，不写内部审批级别。并购模块中「交易负责人」问题仍适用。
- **法务、中大型律所：** 按第 1 部分设计的升级链问。
- **法律援助/诊所：** 转向监督模型框架——谁监督，事项何时上报督导律师？
- **政府：** 适配——机构/办公室内的审批链。

在 `## 公司概况` 中记录 `**执业环境：**` 行。

#### 写入配置

按模板，在配置第一节之后立即写入 `## 谁在用`、`## 可用集成`、`## 输出` 章节。这些决定本插件所有技能的输出头选择和功能回退行为。

### 第 0.5 部分：模块选择（1-2 分钟）

问哪些适用。多个同时适用很常见。一个总法律顾问四项全有也不罕见。

> 这些中哪些是你常规工作的一部分？（这决定执业档案构建哪些章节、哪些技能点亮——只选并购就完全跳过公司治理、上市公司和实体合规访谈。）
>
> 1. **并购交易** —— 买卖、投资、分拆业务单元
> 2. **公司治理与股东会/董事会** —— 董事会/股东会筹备、会议记录、决议、委员会管理、章程修订
> 3. **上市公司合规** —— 信息披露、内幕交易管理、股权激励、交易所规则
> 4. **境内实体合规** —— 子公司管理、注册资本实缴、工商年报、年检、合规期限追踪
>
> 告诉我适用的编号。之后随时用 `/corporate-legal-cn:cold-start-interview --module [name]` 添加模块。

记录激活模块。只进入每个激活模块的章节，其余完全跳过。

### 第 1 部分：公司概况（2 分钟，总是）

无论哪些模块激活，这些问题都适用。

> 问结构化问题之前：你有授权制度、董事会批准的权限矩阵或既往公司治理备忘录可以给我读吗？粘贴内容、分享文件路径，或说『没有』——我会逐个问。分享的话我提取审批级别和升级点，不用你重打。

用户上传：读它，提取公司主体、法务团队规模、升级/授权结构，确认你找到的内容，跳过相应详细问题。

否则：

> **[你的公司] 是做什么的？** 这是最重要的上下文——一家 SaaS 厂商的 playbook、硬件分销商的 playbook、服务公司的 playbook 完全不同。不用打出来：贴公司网站链接、企业介绍、或一句话版：卖什么、卖给谁、怎么卖（直销 / 渠道 / 平台 / 订阅）。

- 公司名称（或输出中想用的名称）？
- 行业？
- 公司主体全称 + 统一社会信用代码（与营业执照一致）？
- 注册地、主要经营地（决定地方监管、法院管辖、数据出境备案受理机关）？
- 法务团队规模——只有你，还是团队？
- 司法管辖足迹（是否有境外主体；决定跨法域识别触发）？
- 「审查发现需要更高层签字的事——尽调中的新问题、重要性门槛决定、有董事利益冲突的决议事项、需要判断的日程项目、或超出你权限的决定——交给谁？给名字或角色（总法律顾问、合伙人、交易负责人），或说『我自己决定』。这是插件知道何时说『你能处理』还是『请 [X] 介入』的依据。（这驱动 /diligence-issue-extraction、/material-contract-schedule、/written-consent 及所有其他技能的升级路由。）」

**若用户未上传授权制度：** 本节结束时提供：「要我把你刚说的升级和权限行写成一份可分享、可维护的独立授权说明吗？同样内容，换成可传阅格式。」

写入配置 `## 公司概况`。

### 第 2M 部分：并购模块（4-6 分钟，若激活）

#### 2M-a：交易立场

- 买方、卖方，还是双方？注：多数公司长期都经历过两侧——这设置整体默认；每交易标志（`--new-deal`）捕捉任一进行中交易的实际立场。
- 系列收购方有标准 playbook，还是每笔交易从零设计？
- 你这边谁主导交易——业务发展部、法务、外部律师牵头，还是混合？

#### 2M-b：尽调结构

> 提问之前：你有标准尽调清单或既往问题备忘录吗？粘贴内容、分享路径，或说『没有』——我逐个问。分享的话我提取类别结构、重要性门槛和本所格式，跳过对应问题。

否则：

- 你有标准尽调清单吗？怎么组织——按职能（法务/财务/人力）还是按文件类型？
- 合同审查的重要性门槛？(全部合同？高于 X 万元？按收入排名前 N？)（这驱动 /diligence-issue-extraction 和 /material-contract-schedule——门槛决定哪些合同全量审查、哪些分诊。）
- 你常用什么数据室——Box、Datasite、飞书文档、网盘，还是别的？
- 你用 AI 辅助审查工具吗——Luminance、Kira，或其他（如合同管理系统内置 AI 抽取、幂律、达观）？具体做什么？

**若用户未上传清单或既往备忘录：** 模块结束时提供：「要我按你所述的重要性和类别结构，起草一份入门尽调清单和问题备忘录骨架吗？基于你告诉我的。下次交易可编辑复用。」

#### 2M-c：问题备忘录格式

> 两样东西：
>
> 1. 你的标准尽调清单——买方用，或卖方侧预期看到的。
> 2. 一份既往交易的问题备忘录——已交割的，不是进行中的。我想看你怎么组织发现：怎么命名、怎么分类、用什么严重级别体系、写到多深。
>
> 这两份文件成为主骨架。你的类别、你的格式、你的标准——不是通用模板。（这驱动 /diligence-issue-extraction——技能在每笔未来交易复用你的章节结构、严重级别方案和发现模板。）

从清单提取：类别结构、重要性门槛（如有）、标准豁免。
从备忘录提取：章节结构、严重级别方案、发现格式、深度、致谁。

#### 2M-d：卖方侧具体问题（若卖方侧激活）

若律师也有卖方工作，追加问：

- 准备数据室时，谁决定什么放进去？
- 你准备披露备忘录或问题日志预判买方的标记吗？
- 数据室填充与业务侧谁协调——业务发展部、财务负责人、各职能负责人？

卖方侧是预判买方的发现、管理信息外流，而不是审入站文件。这决定 set 了卖方侧上下文时 diligence-issue-extraction 技能的行为。

#### 2M-e：交割清单与交易团队简报

- 交割清单放哪——Excel、项目管理系统？
- 谁负责更新？
- 怎么给团队简报——每天、每周、里程碑？邮件、群、电话？
- 业务侧实际看什么，什么只进档案？

写入配置 `## 并购交易`。

### 第 2B 部分：公司治理与股东会/董事会模块（3-4 分钟，若激活）

- 你的正式角色——董事会秘书、董事会秘书助理，还是无正式头衔的顾问角色？
- 董事会多大，构成如何——独立董事多、内部人为主、结构如何？有没有需要设立审计委员会的情形（上市公司法定；非上市公司选设）？
- 有哪些委员会？（审计、薪酬、提名、战略，其他？）
- 董事会材料用什么工具——邮件、办公套件、无正式工具？
- 每年常规董事会/股东会多少次，大致哪几个月？

**会议记录：**
- 长叙事式、决议摘要式，还是中间？
- 会后多久出记录？
- 怎么批准——传阅书面意见，还是下次会议追认？

**书面决议：**
- 你常规用不召开会议的书面决议吗？用于什么类型的董事会或委员会动作——常规高管任命、股权激励、年度动作，还是更广？
- 有什么限制——章程、议事规则限制，还是只是惯例？

**种子会议记录（board-minutes 技能必需）：**

> 上传 5-6 份既往董事会或委员会会议记录。仅已完结会议，无进行中的。这些教技能你的本所格式——记录怎么结构化、讨论细节写到什么程度、决议怎么措辞、出席怎么记录。如有两种格式，全董事会一套和委员会一套。（这驱动 board-minutes 技能——每份未来记录草稿从你提取的结构、讨论深度、决议表述构建。）
>
> 现在没有可分享的记录，之后可用 `/corporate-legal-cn:cold-start-interview --module board` 补。记录技能在缺失时会提示你。

从种子记录提取：
- 整体结构与章节顺序
- 抬头格式（公司名称、会议类型、日期、地点）
- 出席记录格式（董事到会/缺席、管理层、列席）
- 讨论深度——长叙事、决议摘要、混合
- 决议表述（精确措辞）
- 附件引用惯例
- 签署栏格式
- 每套都出现的标准引言或套话

把提取的格式写入配置 `## 董事会与公司秘书` 的 `**会议记录模板：**` 块。

**决议库（written-consent 技能必需）：**

> 你有已签署书面决议的存放文件夹或库吗？（这驱动 /written-consent——技能搜库找最接近的先例决议，不仅用格式，还用该类型动作已批准的具体决议表述。）
>
> 有的话：告诉我位置（文件夹路径、网盘目录）。技能运行时搜索它。
>
> 没有集中库：现在上传 3-5 份既往决议学格式。技能仍可用——只是建库前没有先例搜索能力。

从库或种子决议提取：
- 本所决议表述（精确措辞）
- 引言结构（WHEREAS 段落——考虑到/鉴于 的深度与风格）
- 授权表述（结尾的高管授权）
- 复本与电子签名表述（如有）
- 签署栏格式

写入配置 `## 董事会与公司秘书` → `**决议库：**` 和 `**决议格式：**`。

**年度治理周期：**
- 你管理哪些年度事项？（董事选举/改选、审计机构聘用、股权激励计划批准、年度报告、章程修订——任何适用的。）

写入配置 `## 董事会与公司秘书`。

### 第 2P 部分：上市公司模块（3-4 分钟，若激活）

- 上市交易所——上交所、深交所、北交所？
- 财务年度（一般自然年）？

**信息披露委员会：**

### 第 2E 部分：实体合规模块（2-3 分钟，若激活）

> 有组织架构图或实体清单吗？哪怕粗略、哪怕电子表格——现在上传。我读取并提取实体结构、法域、持股比例、实体类型。这比凭记忆回答问题更准更快。（这驱动 /entity-compliance——技能从这张表初始化合规日历并提示工商年报、注册资本实缴等期限。）
>
> 没有的话，回答下面的问题，我从答案构建入门实体表。

**从上传的架构图或实体清单提取：**
- 实体名称与类型（有限公司、股份公司、有限合伙、分公司、境外实体的 local equivalent）
- 各注册地（境内省/市、境外国家/地区）
- 股权链路与比例
- 标记为休眠或注销中的实体

**无上传则问：**

- 你在管理多少个有效法律实体，大致？
- 关键法域——单一中国境内，还是有境外主体（香港、开曼、BVI、新加坡等）？
- 谁负责营业执照年检/年报公示——法务、财务、还是外部代理？
- 用实体管理系统吗——还是 Excel/表格？
- 股权/期权表情况——用了 Carta 之类的工具，还是手工？（全资无外部股权则不适用；有对赌/员工激励则适用）
- 谁做常规申报——工商年报、税务申报、社保、外汇?
- 子公司有自己的治理节奏，还是实际上只是休眠持股壳？
- 有内部关联协议吗——服务协议、IP 许可、贷款、资金归集?

写入配置 `## 境内实体合规`。

## 每交易设置（`--new-deal`，仅并购模块）

进行中交易启动时，跑一个只关注交易特定上下文的轻量访谈。整体方法仍来自插件配置。

问：
- 交易代码名
- 本交易的立场（买方或卖方——可能不同于整体默认）
- 目标方或收购方名称
- 数据室位置（文件夹路径或 URL）
- 交易负责人姓名
- 签约日和交割日（如已知）
- 本交易特定的门槛差异（5000 万级交易审查的合同可能比 10 亿级更细）
- 本交易外部律所和牵头联系人

写入 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/deals/[code-name]/deal-context.md`。技能同时读插件配置（整体）和 `deal-context.md`（本交易），冲突时 deal-context.md 优先。

## 失败模式

- **不要假设所有模块都激活。** 先问，只访谈实际有效的。只做交易的律师不需要上市公司治理设置。
- **不要硬编码买方。** 档案捕捉整体倾向；每交易标志处理实际立场。整体档案写成立场中性；姿态在 `--new-deal` 时按交易设置。
- **不要写通用占位符。** 答案含糊（「标准重要性门槛」）时，问清楚数字。档案只有门槛是实际门槛才有用。
- **卖方姿态不是买方反转。** 卖方侧是预判买方发现、管理外流信息，而不是审入站文件。卖方侧激活时标出这个区别。
- **不要为未激活模块索要种子文件。** 只有并购激活才要清单和备忘录。只做董事会的律师不需要提供尽调文件。
- **不要问「哪家交易所」处理非上市公司。** 上市公司模块只对上市公司有意义；非上市公司选 2B 公司治理模块。
