# /integration-management

1. 加载 `deal-context.md` 取交易代码、目标公司、交割日、交易负责人。
2. 若 `integration-tracker.yaml` 存在则加载（否则 `--init` 时创建）。
3. 用下面的工作流。
4. 按标志路由：
   - `--init`：模式 1——读收购协议、构建阶段化工作计划、同意追踪器
   - `--contracts`：模式 2——导入合同清单（库或上传）、分层与分类
   - `--report`：模式 3——生成状态报告
   - `--update`：模式 4——手动更新或解析上传的状态文档
   - `--export`：模式 5——CSV 或表格导出
5. 读/写 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/deals/[code]/integration-tracker.yaml`。
6. 每次写后：显示改动摘要并浮现新标记。

## 事项上下文

**事项上下文。** 检查执业档案 CLAUDE.md 中的 `## 事项工作区`。若 `启用` 为 `✗`（法务用户的默认值），跳过本段其余内容。若已启用且没有活动事项，询问：「这是哪个事项？运行 `/corporate-legal-cn:matter-workspace switch <slug>` 或说『执业层』。」加载活动事项的 `matter.md`。输出写入事项文件夹。除非 `跨事项上下文` 为 `开`，绝不读取其他事项的文件。

## 用途

外部律师完成交割。法务承接烂摊子。本技能是交割后整合的项目管理层——不是业务整合、不是 IT 系统、不是 HR 组织设计。法务工作流：同意、合同转让、实体理顺（合并/注销/存续）、IP 变更登记、协议下的持续义务。它追踪什么已做、什么到期、什么阻塞、什么需要决策。

## 模式 1：初始化

```
/corporate-legal-cn:integration-management --init [--deal [code]]
```

### 第 1 步：加载交易上下文

读 `deal-context.md`。未找到：问交易代码、目标公司、交割日、交易负责人、外部律师。若不存在则写入 `deal-context.md`。

读 `closing-checklist.yaml`（若存在）。任何标为交割后的项目成为 Day 1 或 Day 30 工作项（继承状态）。

### 第 2 步：读取交易输入

**完整的收购协议产出最完整的追踪器。** 协议的「必需同意」清单和交割后承诺章节是硬性期限和法律义务的权威来源。但技能可以从任何可得内容有用地初始化——部分输入产出律师补齐的入门追踪器，而不是空白页。

> 你有哪些交易资料？分享现有的：
>
> **理想：** 收购协议（上传或连接文档路径）。我会读交割后承诺、必需同意清单、陈述与保证存续期、支付托管条款、业绩承诺条款。
>
> **也有用——分享任何组合：**
> - 交易摘要或条款清单（关键商业条款和时间线）
> - 外部律师的整合待办清单或交割后清单
> - 现有工作计划或整合追踪器（我导入并接续）
> - 交割清单——若由 M&A 冷启动技能生成，我从 `closing-checklist.yaml` 自动继承
> - 单独的必需同意清单（若协议由外部律师保管）
>
> **如什么都没写下来：** 用大白话告诉我交易——谁被收购、何时交割、主要未决项——我从标准 Day 1/30/90/180 工作计划构建入门追踪器供你编辑。

**从协议提取：**

*必需同意清单：*
- 对每项同意：相对方名称、合同类型、合同期限。设 required_consent: true 并填 pa_deadline。

*交割后义务：*
- 每项义务映射到工作项。按期限分配到正确阶段。deadline_basis 标为「协议义务」。

*关键日期：*
- 必需同意期限——从协议提取
- 陈述与保证存续期——从协议逐一提取（一般陈述、基础陈述、税务/劳动/环保等特别陈述通常存续期不同；不要假设默认）
- 支付托管释放日——从协议提取
- 业绩承诺（对赌）计量与支付日——加到 pa_dates.earnout_milestones，owner 总是设为「finance」（法务只追踪日期）

### 第 3 步：构建阶段化工作计划

为每个阶段生成标准工作项。加上第 2 步提取的协议义务。从交割清单继承的项目预填充。

**Day 1 — 法务主导：**
- 工商变更登记（股东变更、法定代表人变更、董事/监事/高管变更） `[优先级：关键]`
- 银行账户预留印鉴/网银人员变更通知（凭交割文件通知开户行） `[优先级：关键]`
- 关键 IP 变更登记（专利、商标转让登记——国家知识产权局；著作权登记——中国版权保护中心） `[优先级：关键]`
- 域名、公众号、社交账号主体变更 `[优先级：高]`
- 董监高责任险（D&O）——若安排离任董事拖延险 `[优先级：关键]`
- 印章交接（公章、财务章、合同章、发票章、法定代表人章）——盖章效力在中国实务中至关重要 `[优先级：关键]`

**Day 1 — 法务支持：**
- 员工公告与沟通（HR 主导，法务审阅法律合规性）
- 员工社保公积金主体变更（HR 主导，法务审阅劳动合同延续）
- 客户/合作方沟通函（业务主导，法务审阅准确性）

**Day 30 — 法务主导：**
- 必需同意首轮推进——联系所有相对方，记录发函 `[优先级：关键]`
- 国家知识产权局办理专利、商标转让登记 `[优先级：高]`
- 著作权变更登记 `[优先级：中]`
- 重大合同审查——完成 tier 1 和 tier 2 合同转让分析 `[优先级：高]`
- 章程修订与股东会决议归档 `[优先级：高]`

**Day 30 — 法务支持：**
- 数据迁移的合规审查（IT 主导，法务对**个人信息处理者变更**、**数据出境**、跨境访问机制建议——个保法第 23 条个人信息提供的告知与单独同意）
- 房屋租赁合同的转让条款审查（物业主导，法务咨询——租赁合同的承租人变更多需出租人同意）

**Day 90 — 法务主导：**
- 必需同意期限——所有必需同意必须取得或上升 `[优先级：关键，期限：pa_dates.required_consents_deadline]`
- 实体理顺决定——建议保留 / 合并 / 注销 `[优先级：高]`
- 员工社保、公积金、住房补贴等安排的过渡文档 `[优先级：高]`
- 次要同意推进——剩余未决同意 `[优先级：高]`
- Tier 3 控制权变更合同处理 `[优先级：关键]`

**Day 90 — 法务支持：**
- HR 制度并轨文档（HR 主导，法务咨询劳动法——员工手册、绩效制度变更需履行民主程序，劳动合同法第 4 条）

**Day 180 — 法务主导：**
- 合并变更登记——如理顺决定是合并（须履行编制资产负债表、通知债权人、公告等法定程序） `[优先级：高]`
- 注销登记——如决定注销（须履行清算、通知债权人、税务注销等法定程序） `[优先级：高]`
- 完整合同变更主体（novation）——需以收购方名义的合同 `[优先级：高]`
- 陈述与保证存续期追踪——记录即将到期日 `[优先级：中]`

生成后显示摘要。

## 模式 2：合同转让

```
/corporate-legal-cn:integration-management --contracts [--deal [code]]
```

专门的合同转让初始化。与主 init 分开，可独立运行、合同清单变化时重跑。

### 第 1 步：获取合同清单

两条路径——用适用的：

**路径 A：连接的库**

> 你的合同库连接了吗？（Google Drive、Box、飞书文档、SharePoint，或交割后仍可访问的 VDR？）
>
> 是：给我目标公司合同的文件夹路径或名称。我会拉取清单并读每份合同的转让条款和相对方。

搜索连接的库。对每份文档：提取文件名和路径；读文档——识别合同相对方、合同类型、转让条款文本、控制权变更条款文本（如有）、年度金额（如载明）。

**路径 B：手动清单上传**

> 上传合同清单。可以是：
> - 协议披露清单中的重大合同章节
> - 合同管理系统的 CSV 或 Excel 导出
> - 手工准备的清单
>
> 最少必需列：合同名称、相对方。有用但可选：合同类型、年度金额、转让条款原文。

读上传清单。对无转让条款原文的合同，assignment_mechanism 设为 "not_reviewed" 并标记待跟进。

**路径 C：披露清单**

若库和清单都没有，从收购协议披露清单读重大合同章节。这给出最少清单——相对方和合同类型。转让条款需人工审查。

### 第 2 步：判断转让机制

对每份合同，分类转让机制：

| 机制 | 定义 | 层级 |
|---|---|---|
| `consent-required` | 明确禁止未经同意转让的条款 | 1 或 2 |
| `coc-provision` | 控制权变更条款赋予相对方交易触发的终止或同意权 | 3 |
| `auto-assign` | 无限制，或明示允许向关联方或承继方转让 | 4 |
| `silent` | 无转让条款——按适用法默认规则处理。中国合同法（民法典合同编）下**合同权利转让原则上需通知债务人**（民法典第 546 条 `[待核验条文号]`）**合同义务转让原则上需债权人同意**（民法典第 551 条 `[待核验条文号]`）——因此「silent」的合同是否可自由转让需具体分析权利义务性质。标注供律师审查。 | 2 |
| `not_reviewed` | 无法读或定位转让条款 | 标记待人工审查 |

对协议「必需同意」清单标记的合同：不论转让机制分类，覆盖为 tier 1。

### 第 3 步：分层

```
Tier 1 — 必需同意：[N] 份合同
  列入协议清单，硬期限 [日期]，必须取得同意

Tier 2 — 重大、需同意：[N] 份合同
  存在转让限制，不在协议清单中
  建议时间线：Day 90 内取得

Tier 3 — 控制权变更条款：[N] 份合同 ⚠️
  相对方对交割有终止或同意权
  须动作：立即联系相对方——CoC 可能已触发

Tier 4 — 自动转让 / 无动作：[N] 份合同
  按关联方/承继方条款自动转让
  仅追踪——无需发函

未审：[N] 份合同
  无法判定转让机制——须人工审查
```

Tier 3 单独且显眼展示。控制权变更条款可能在交割日已触发——相对方可能有正在计算的终止权。

### 第 4 步：生成状态条目

对每份合同创建追踪器条目：全部提取字段（相对方、类型、金额、机制、层级）；初始状态：tier 4 → `无需动作`；tier 3 → `CoC 已触发`；tiers 1/2 → `同意未决`；未审 → `未审`；pa_deadline 从必需同意清单填 tier 1。

```
/corporate-legal-cn:integration-management --update [--deal [code]]
```

**手动更新：** 律师告知 Claude 变化。

## 本 skill 不做的事

- 不管理业务整合工作流（IT、HR、财务、不动产）。它追踪法务在这些工作流中的接触点并标记法务输入需要时。所有权留在业务职能。
- 不起草同意请求函或转让协议——那由 written-consent 技能或外部律师产出。
- 不就赔偿请求或协议违约提供意见。同意被拒或期限未达时它标记情况——法律分析后果是律师的事。
- 不追踪对赌业绩。业绩承诺里程碑和支付日在追踪器中作为参考日期，owner 设为 finance。业务驱动数字。
- 不实时读合同做状态报告。合同状态是律师在追踪器中更新的。技能在报告时读追踪器，不读合同。

## 表格公式注入防御

在 Excel、表格或 CSV 输出中写入任何单元格前，中和公式注入。相对方来源文本（合同摘录、相对方名称、代理数据、合同管理系统导出）是攻击者可控。以 `=`、`+`、`-`、`@`、制表符、回车、换行开头的单元格会被当作公式或破坏行结构。

- **前缀单引号：** `'=SUM(A1:A10)` → 显示为文本，不执行
- **适用于每个含文档、工具结果或用户粘贴来源文本的单元格。**
- **CSV：还要转义嵌入的逗号、双引号、换行**（RFC 4180 引用）。
