# /renewal-tracker

列出哪些合同将续约、以及必须在什么时候之前发出不续约通知。

## 说明

1. **读 `~/.claude/plugins/config/claude-for-legal-cn/commercial-legal-cn/renewal-register.yaml`**（配置目录 —— 插件更新后仍保留）。

2. **默认模式：** 模式 2 —— 未来 90 天内快到的，按紧急度分组，用半开区间让每个截止日只落进一个档：🔴 0–13 天，🟠 14–44 天，🟡 45–89 天。第 14、45、90 天是边界，各归一档，不重复。

3. **`--days N`：** 改变窗口。

4. **`--missed`：** 模式 4 —— 通知截止日已过但无解除/不续约记录的。

5. **登记表为空且合同管理系统已连接时：** 提供模式 3 —— 扫描系统里有续约日期的在生效合同，批量导入。

6. **输出含建议动作：** 该找谁（每条登记里的业务负责人）、哪些价格无上限（窗口关闭前先拿到备选报价，保留筹码）。

## 示例

```
/commercial-legal-cn:renewal-tracker
```

```
/commercial-legal-cn:renewal-tracker --days 180
```

```
/commercial-legal-cn:renewal-tracker --missed
```

---

## 目的

没人会把一份合同读两遍。续约日期在审查时提取一次，然后存在某处 —— 最好是能在不续约截止日前 45 天冲你喊、而不是过后 45 天才提醒的地方。

本技能维护续约登记表并列出快到的。

## 登记表

存在 `~/.claude/plugins/config/claude-for-legal-cn/commercial-legal-cn/renewal-register.yaml`（配置目录 —— 插件更新后仍保留）。每条：

```yaml
- counterparty: "某云服务有限公司"
  agreement: "某云平台软件服务合同"
  signed_date: 2025-06-15
  initial_term_end: 2026-06-15
  current_term_end: 2026-06-15     # 每次自动续约后前滚；cancel_by_* 从这个字段算
  renewal_mechanism: "自动续约（年度）"
  notice_period_days: 60
  notice_method: "email"           # email / 平台内操作 / 公证送达 / EMS/挂号信 / 按合同第X条
  transit_buffer_days: 0           # 电子 0，境内挂号信 5，境外邮寄 10 —— 或按合同约定
  cancel_by_calendar: 2026-04-16    # current_term_end 减 notice_period_days
  cancel_by_effective: 2026-04-16   # 需要时回滚到最后一个工作日
  send_by_effective: 2026-04-16     # cancel_by_effective 减 transit_buffer_days —— 必须发出通知的日期
  cancel_by_roll_note: ""           # 例如「从周日 2026-11-01 回滚；按合同工作日定义核验」
  cancel_by_provenance: "[模型计算 —— 按通知条款核验]"
  price_on_renewal: "届时牌价（无上限）"
  annual_value: 480000
  business_owner: "张三 zhangsan@company.com"
  clm_id:        "HT-12345"        # 若已连接合同管理系统
  esign_id:      "fadada-abc-123"  # 若已连接电子签章平台
  status: "active"               # active | cancelled | renewed | lapsed
  notes: "价格无上限 —— 续约前重新评估。备选供应商：X、Y。"
```

**通知在途时间 —— 按 `send_by_effective` 预警，不是 `cancel_by_effective`。** 一个要求公证送达或挂号信的 60 天窗口实际只有约 55 天。按「送达日」预警的追踪器就是会错过截止日的追踪器。计算 `send_by_effective = cancel_by_effective - transit_buffer_days`，紧急度档（模式 2 的 🔴/🟠/🟡）按 `send_by_effective` 触发。模式 2 紧急度列显示 `send_by_effective`；明细列显示 `cancel_by_effective`、`notice_method`、`transit_buffer_days`，让读者看到差值并质疑缓冲。

*中国送达实务：* 电子邮件/平台通知在途为 0，但要留存送达证据（对方确认、系统回执）；EMS/挂号信留存底单与妥投记录；重大合同的解除通知建议公证送达或律师函，在途更长，`transit_buffer_days` 相应加大。

**滚动续约 —— 不前滚的登记表只对一次。** 记录里存 `initial_term_end`，但 `cancel_by_*` 从 `current_term_end` 算。续约触发时（窗口已过且未发通知）提示：

> 本合同已于 [日期] 自动续约。更新登记：新 `current_term_end` 为 [日期 + 续约周期]，新 `cancel_by_effective` 为 [计算值]，新 `send_by_effective` 为 [计算值]。确认？

过了第一年，`initial_term_end` 就是错的，只有 `current_term_end` 能算出正确的通知截止日。

## 每个通知截止日都做工作日检查

**登记表的通知截止日必须是通知生效的最后一个工作日，不是日历日。** 落在周末或法定节假日的日历日，是续约截止日被错过的最常见原因。登记表负责抓住它。

计算（或导入）一个通知截止日时：

1. **算出日历日。** `cancel_by_calendar = current_term_end − notice_period_days`（或条款指定的）。这是原始算术。
2. **按中国法定节假日回滚。** 用国务院办公厅每年发布的节假日安排（含调休 —— 调休上班日算工作日，调休放假日不算）。若落在周六、周日或法定节假日，**回滚**到前一个工作日。永远回滚，不前移 —— 前移意味着通知在窗口关闭后才到。跨年的春节、国庆长假尤其要注意；节假日安排通常上一年底才发布，若目标日期在尚未发布安排的年度，标注「[节假日安排待发布 —— 临近时按国办通知核验]」。
3. **查合同自己的计日规则。** 找「工作日」「送达」「视为送达」「下午 5 点前」或通知方式条款。若合同定义了「工作日」或指定了送达机制（公证送达、邮寄回执、邮件已读回执），以合同定义为准。标出默认回滚与合同自身规则的任何不一致。
4. **登记表同时记两个日期。** `cancel_by_calendar` 是原始算术；`cancel_by_effective` 是通知生效的最后一个工作日；`cancel_by_roll_note` 记录二者为何不同（如「从周日 2026-11-01 回滚；按合同工作日定义核验」）。每个算出的 `cancel_by_effective` 带 `cancel_by_provenance` 标注 `[模型计算 —— 按通知条款核验]`，让核验标记跟着日期走，而不是跟着周围文字。
5. **按生效日触发预警，不是日历日。** 紧急度档（模式 2 的 🔴/🟠/🟡）用 `cancel_by_effective`（经在途缓冲后即 `send_by_effective`）。

一份模式 2 报告若打印 `cancel_by: 2026-10-01`（国庆假期）却没标星期、没警告，就是一个静默错误的生效截止日。登记表是抓住它的地方 —— 在导入时抓一次，而不是窗口已经移走之后。

## 模式

### 模式 1：导入一条续约（来自审查的移交）

当 saas-msa-review 或 vendor-agreement-review 发现续约条款，它移交一条记录。追加到登记表。若相对方已有条目，问这是替换（续约后的协议）还是新增协议。

### 模式 2：快到的

**默认回看窗口：** 未来 90 天。

**紧急度档是半开区间 —— 一个截止日只属于一个档。** 用「距通知截止日天数」（`send_by_effective - 今天`）。第 14、45、90 天各属一档，不属两档；这里差一天会把最紧急的项落进不那么紧急的桶。

- 🔴 **0–13 天**（不足 14 天 —— 含今天）
- 🟠 **14–44 天**
- 🟡 **45–89 天**
- （90 天以上在默认回看窗口外；仅当用户传了超过 90 的 `--days` 时纳入）

```markdown
## 续约 —— 未来 90 天

### 🔴 通知截止日在 0–13 天内

| 相对方 | 须于此前发出 | 续约日 | 年金额 | 负责人 | 备注 |
|---|---|---|---|---|---|
| [名称] | **[日期]** | [日期] | [金额] | [邮箱] | [备注] |

### 🟠 通知截止日在 14–44 天内

[同表]

### 🟡 通知截止日在 45–89 天内

[同表]

---

**建议动作：**
- [ ] [相对方] —— 找 [业务负责人]：这个还要不要续？
- [ ] [相对方] —— 价格无上限；在失去筹码前先拿一份备选报价
```

若窗口内登记超过约 10 条，或用户要求：提供仪表盘（见档案 `## 输出`）。

### 模式 3：扫描合同管理系统 / 电子签章平台以填充登记表

若 MCP 已连接且登记表为空或陈旧：

1. 查合同管理系统里所有状态为「生效/已签」且有续约日期字段的合同
2. 查电子签章平台近 24 个月完成的、元数据含「订阅」「续约」「自动续约」的签署件
3. 对每条命中，提取续约机制加入登记表
4. 标出续约日期无法从元数据判断的 —— 那些需要人读合同

这是一次性批量导入。之后导入发生在审查时。

### 模式 4：已错过的窗口（坏消息报告）

```markdown
## 已错过的不续约窗口

以下合同的通知截止日已过，且无解除/不续约记录：

| 相对方 | 截止日曾是 | 续约日 | 状态 |
|---|---|---|---|
| [名称] | [日期] | [日期] | 将于 [日期] 自动续约 |

**选项：**
- 协商逾期解除（很少成功但值得一问）
- 接受续约，现在就标好明年的通知截止日
- 查合同有无其他解除权（任意解除、法定解除 —— 民法典第 563 条）
```

## 关口：接受或拒绝一次续约

追踪续约日期是研究。**行动** —— 发出不续约通知、放任自动续约触发、或回签续约单 —— 是有法律后果的一步。

**在接受或拒绝续约（含发出不续约通知，或放任自动续约越过通知截止日）之前：** 读档案 `## 谁在用`。若角色是非律师：

> 这一步有法律后果（你要么承诺再来一个期限，要么终止关系）。你和律师确认过了吗？确认过就继续。没有的话，这是一页纸带给律师：
>
> [生成一页纸摘要：相对方、当前期限终止日与通知截止日、续约价格机制、什么都不做会怎样、想换供应商时的备选，以及窗口关闭前要问律师的三件事。]
>
> 需要找律师的话：联系当地律师协会、法律援助机构或公共法律服务中心获取转介。

未获明确「是」，不越过此关口。

## 集成：renewal-watcher agent

本插件的 renewal-watcher agent 按计划（默认每周）运行本技能，把「快到的」报告发到档案 `## 文风` / 工作产物去处指定的渠道（企业微信 / 钉钉 / 飞书群）。模式 2 是该 agent 的主要输出。

## 本 skill 不做的事

- 不解除合同。它告诉你什么时候该决定。
- 不决定是否续约。它列出截止日和业务负责人。
- 不读合同去找续约日期 —— 那发生在审查时。若一份合同在登记表里却没有续约日期，说明是手动加的，需要有人补上。

## 质量自检（本技能转换说明）

- **A 级直转：** 登记表 YAML 结构、四种模式、紧急度半开区间、按发出日预警、滚动续约前滚、数据密集提供仪表盘 —— 方法论层原样保留。
- **B 级大改：** 工作日回滚从「美国联邦/州节假日」改为「国务院办公厅节假日安排 + 调休」；通知方式从 certified mail 改为公证送达/EMS/挂号信/平台通知并强调送达证据；CLM/DocuSign 改为合同管理系统/电子签章平台；解除权引用民法典第 563 条；非律师关口的转介渠道改为中国律协/法援。
- **C 级删除：** 无英美法特有概念残留（原「certified mail」「federal holidays」已中国化）。
- **D 级新增：** 无独立新增。
