# /tabular-review

1. 加载 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/CLAUDE.md` → 尽调结构、门槛、本所格式。
2. 确认：什么文档、什么列、输出去哪。
3. 构建带类型的 schema。写 `.review-schema.yaml`。与用户确认。
4. 样本运行（3-5 份）。调整 schema。确认。
5. 展开——每份文档一个子代理，并行。每个单元格：值 + 状态 + 逐字引用 + 位置。
6. 归一化通过。标记异常值和不一致。
7. 输出：`.xlsx` 或飞书表格（问哪个），加 `.csv` + `_sources.csv` + markdown 总是有。待审核草稿头。
8. 摘要：核验工作量（每列 not_present / unclear / needs_review 计数）、标记列、文件位置、提醒每个单元格都是线索不是结论。

```
/corporate-legal-cn:tabular-review
/corporate-legal-cn:tabular-review --schema .review-schema.yaml --docs ./vdr/02-合同/
/corporate-legal-cn:tabular-review --template ma-diligence
```

**`--schema <path>`：** 用现有 schema 文件而不是构建新的。适合重跑和增量添加。

**`--template <name>`：** 从 `references/` 中的模板开始。目前：`ma-diligence`。

**`--docs <path>`：** 文档来源。本地文件夹、飞书文档 ID、或 VDR 路径。省略则询问。

**`--output <xlsx|gsheets|csv>`：** 输出格式。省略则询问。

**`--sample <n>`：** schema 检查的样本大小。默认 5。

## 用途

你有一堆文档和一串需要在每份上一致回答的问题。尽调清单。供应商合同审计。租赁组合审查。输出是一张表：文档行、数据点列，每个单元格可追溯到源文档中的精确措辞。

这不是问题识别。`diligence-issue-extraction` 从 2000 份文档中找出 30 个隐藏问题。本技能对所有 2000 份回答同样的 15 个问题。两者都合理；回答不同问题。

这也不是替代人工读文档。本技能产出的每个单元格是**需核验的线索**，不是发现。输出的设计让核验变快，不是让核验被跳过。

## 列类型系统

表格化审查有用的关键：C 列在第 1 行和第 200 行意思一样。自由文本会漂移。类型不会。

每列有**类型**，约束答案格式：

| 类型 | 返回什么 | 用于 |
|---|---|---|
| `verbatim` | 从文档精确引用，字符对字符 | 定义术语、操作性条款措辞、任何字词至关重要处 |
| `classify` | 你定义的固定清单中的一个值 | 是/否、有/无、条款变体（如「独家同意」/「不得无理拒绝的同意」/「未约定」） |
| `date` | ISO 日期 | 生效日、到期日、终止通知期限 |
| `duration` | 数字 + 单位 | 期限、通知期、存续期 |
| `currency` | 数字 + 币种 | 上限、门槛、费用、交易价格引用 |
| `number` | 纯数字 | 计数、百分比、页码引用 |
| `free` | 短自由文本摘要 | 谨慎使用——这类型会漂移。只在其他类型确实不适用时用 |

**逐字规则：** 每个非 `verbatim` 列也捕获支持答案的精确源引用，作为伴生字段。单元格中的答案是解释；引用是证据。一个 `classify` 单元格说「不得无理拒绝的同意」，如果没有它来自的那句话就没用，因为审阅者的工作是检查这是否正确解读。

## 「未找到」的三种状态

空白单元格隐藏信息。任何时候不能产出正面答案，强制三种明确状态之一：

| 状态 | 含义 | 何时用 |
|---|---|---|
| `not_present` | 文档已读，该条款不在 | 你确信这一主题未涉及 |
| `unclear` | 有东西但你不能自信分类 | 表述模糊、部分条款、条款相互冲突 |
| `needs_review` | 你找到东西但需人工判断 | 边缘情况、异常措辞、答案取决于 schema 未捕捉的判断 |

这是三条不同信息。交易团队处理「合同对转让未约定」和「转让条款模糊」的方式完全不同。压缩成一个空白单元格丢失了这个区别。

## 工作流

### 第 0 步：什么和哪里

确认：
1. **文档。** 在哪？VDR MCP（Box、Datasite、飞书文档）、本地文件夹、Google Drive 文件夹、或文件清单。多少份？>200 时警告要花一段时间，提议从重要性筛选的子集开始。
2. **Schema。** 什么列？两条路径：
   - 用户从 `references/` 选模板（并购尽调标准默认）
   - 用户用自然语言描述列，你构建为类型化 schema
3. **输出。** Excel（`.xlsx`）或飞书表格——问团队用哪个。CSV 和 markdown 总是作为回退写出。输出到交易文件夹、云盘、或用户指定处。

### 第 1 步：构建并确认 schema

把用户的列清单变成结构化 schema。每列：稳定 `id`、人类 `label`、`type`、`prompt`（读文档的审阅者会问的问题），`classify` 列有 `options` 清单。

写入 `.review-schema.yaml`，与输出并列。此文件是可复用产物——用户可编辑、加列、对新文档重跑。展示给用户并在展开前确认。

```yaml
schema:
  name: "并购尽调 — 项目 [代码]"
  created: 2026-05-07
  columns:
    - id: counterparty
      label: "相对方"
      type: verbatim
      prompt: "除目标公司外的合同方是谁？逐字引用。"
    - id: effective_date
      label: "生效日"
      type: date
      prompt: "协议何时生效？"
    - id: change_of_control
      label: "控制权变更"
      type: classify
      options: [未约定, 需同意, 不得无理拒绝的同意, 自动终止, 仅通知]
      prompt: "协议是否处理目标公司的控制权变更？规定了什么？"
    - id: assignment
      label: "转让限制"
      type: classify
      options: [未约定, 需同意, 不得无理拒绝的同意, 可自由转让, 可向关联方转让]
      prompt: "目标能转让本协议吗？有什么限制？"
    # ... 更多列
```

### 第 2 步：样本运行

不要在未测试的 schema 上展开到 200 份。先跑 3-5 份。展示行给用户。检查：
- 大多数答案是 `unclear` 的列——prompt 模糊，重写
- `classify` 列答案不匹配选项——加选项或改为 `free`
- `verbatim` 列返回意译——强调必须字符对字符

调整 schema，重跑样本，确认。这省下用户扔掉全量运行的成本。

### 第 3 步：展开

每份文档一个子代理，并行。每个子代理：

1. 读完整文档（不是 RAG 片段——整份）。
2. 对每列，找到相关条款。
3. 返回结构化行：每列 `{value, state, quote, location}`。
   - `value` 是类型化答案（或 null 如果 `state` 不是 `answered`）
   - `state` 是 `answered | not_present | unclear | needs_review`
   - `quote` 是逐字支持文本（精确，无意译，句中无省略号——要剪就在句边界剪并标记）
   - `location` 是引用所在处（章节号、标题、页码——文档给了什么用什么）

**引用不是可选的，逐字规则是机械的，不是劝说。** 每个子代理在返回带 `state: answered` 的单元格前必须遵守：

- `quote` 必须是源文档中连续文本的字符对字符复制，可在子代理引用的 `location` 检索。不要从章节标题加你预期存在的标准套话组合出引用。不要意译并称之为逐字。不要凭对该类条款「通常」如何写的记忆重构引用。不要用省略号拼接不连续文本填补源中的缺口。
- `location` 必须足够具体，让归一化通过能重新打开文档并重读同一段——章节号、标题、或审阅者可导航到的页码引用。
- 若子代理无法定位并复制精确文本（源截断、OCR 乱码、条款暗含但未写、章节标题可见但正文未加载），单元格状态为 `needs_review`，`value` 为 null，`notes` 必须含 `quote_unavailable: <原因>`。绝不接受用组合或重构引用设 `state: answered`。
- 同规则适用于 `verbatim` 类型列**以及**附加到 `classify` / `date` / `duration` / `currency` / `number` / `free` 单元格的伴生源引用。支持引用承担与单元格值相同的逐字义务。

第 4 步的归一化通过通过在引用的 `location` 重读源文档并把存储的 `quote` 与源文本字符对字符比对来抽查。不匹配把单元格降级为 `needs_review`，注记 `quote_mismatch`，并把整列标为需要更广抽检——若一个子代理组合了引用，同批其他也可能。

### 第 4 步：归一化

展开后，逐列读整表。这一步捕获每个表格化审查工具的失败模式：同一条款在不同文档间被不一致解读。

对每个 `classify` 列：
- 检查每个 `answered` 值都在选项清单中。异常值被重分类或升级为 `needs_review`。
- 查看聚集：若 180 份文档说 `需同意`、20 份说 `不得无理拒绝的同意`，那可能是真实。若 195 份说 `需同意`、5 份说 `可自由转让`，看那 5 份——它们要么真的不同要么被错分。

对每个 `date` / `duration` / `currency` 列：
- 检查格式一致性。归一化。
- 标记不可信值（99 年期限、1 元上限）为 `needs_review`。

对每个 `verbatim` 列**以及**每个其他列上的伴生源引用：
- 通过在引用的 `location` 重开源文档抽查随机样本（每列至少 3-5 行，或 10% 的行，取较大者）并把存储的 `quote` 与源字符对字符比对。
- 若任何引用被组合、意译、重构或不能在引用段定位：把该单元格降级为 `needs_review`，notes 中 `quote_mismatch`，并标整列——把抽检扩大到列的其余部分，而不是假设其他行干净。一个捏造的引用就足以证明扩大检查合理。
- 一个 `state: answered` 且引用不匹配的单元格比 `unclear` 或 `needs_review` 更严重——它误示证据链。积极降级。

### 第 5 步：输出

以三种格式写表：

**Markdown**（总是，用于会话内审查）：
```markdown
| 文档 | 相对方 | 生效日 | 控制权变更 | 转让 | ⚠️ 标记 |
|---|---|---|---|---|---|
| 供应商主协议 — XX | XX 公司 | 2023-04-01 | 需同意 | 需同意 | — |
| 供应协议 — YY | YY 有限 | 2021-11-15 | ⚠️ unclear | 未约定 | CoC 表述模糊 §14.2 |
```

**CSV**（`.csv`，总是）：
一份文件放值，伴生文件放引用和位置（`_sources.csv`）。保持主文件干净，证据链完整。

**Excel**（`.xlsx`）或**飞书表格**——用户实际工作的那个。问；不要猜。两者遵循同样的工作簿结构（见 `references/excel-output.md` 和 `references/gsheets-output.md`）。工作簿输出中：
- 每个数据列配一个隐藏源列，含引用和位置。可见列上的单元格批注在悬停时浮现引用。
- 按状态着色：白色 = answered，黄色 = unclear 或 needs_review，灰色 = not_present。
- 每个数据列后加 `已核验` 列，默认空白。审阅者标记。这是让表可审计的核验/标记模式——交易团队一眼看出人工实际检查了什么。
- `_schema` 表含列定义，文件自文档化。

在顶部前置档案 `## 输出` 的待审核草稿头。同侧含分发说明：

> 本审查源自可能保密的源文档。它继承来源的保密性——分发超出知悉范围可能造成泄密。与事项保密文件一同存放，审慎决定分发。

### 第 6 步：摘要

表写完后，给用户一屏读物：
- 文档数、列数、完成行数
- 每列 `not_present`、`unclear`、`needs_review` 计数——这是核验工作量
- 归一化通过标记 >10% 行的任何列
- 输出文件位置
- 提醒：每个单元格是线索，不是发现。核验后再让它给陈述、清单或备忘录提供依据。

## 收尾：下一步决策树

结尾按 CLAUDE.md `## 输出` 给出下一步决策树。按本技能刚产出的内容定制选项——五个默认分支（起草 X、升级、补充事实、观察等待、其他）是起点，不是锁死项。

## 本 skill 不做的事

- **不替代读文档。** 它告诉你去哪看。
- **不产出置信度分数。** 0.73 不是信息。`unclear` / `needs_review` 状态和逐字引用是置信度信号——引用不支持值就标记。
- **不静默跳过文档。** 用户指向的每份文档都得到一行。读不了的文档得到 `needs_review` 一行加注记。
- **不假装意译是引用。** 证据链是整个要点。

## 与其他技能的关系

- `diligence-issue-extraction` 找问题；本技能抽数据点。若一次抽取揭示问题（引用具体业绩目标的 MAC 条款、毒丸），标记并建议对该文档跑 diligence-issue-extraction。
- `material-contract-schedule` 构建一张具体表（披露清单）。它可直接消费本技能输出——清单是表格化审查的筛选、重排视图。
- `ai-tool-handoff` 在语料过大或团队偏好专用平台时，把批量审查交给 Luminance/Kira。本技能是它可处理任何内容的内部选择——先跑本技能，剩余部分交出去。

## 输出防护

每份输出加待审核草稿头。每个单元格有源引用或标记状态。摘要明说需核验。Excel `已核验` 列使核验状态可审计。这不是让你跳过读的工具；是让读变快的工具。

## 质量自检

本次转换决策：本技能为 A 级直转。表格化审查是通用批量抽取框架，与法域无关——列类型系统、三状态未找到、样本-展开-归一化-输出工作流、逐字规则、位置抽查、Excel/表格双输出全部保留。替换的：路径、命令前缀改为 cn；classify 选项例子改为中文（未约定、需同意、不得无理拒绝的同意、自动终止、仅通知）；Google Sheets 替换为飞书表格作为常见国内选择（并保留 gsheets-output.md 作为跨境语境备用参考）；保密工作产品头替换为待审核草稿头。references/ 下三份配套文件同步转换。
