# /oss-review

按 `~/.claude/plugins/config/claude-for-legal-cn/ip-legal-cn/CLAUDE.md` 执业档案跑开源许可证合规检查。按许可证族分类依赖、映射义务到部署模型、标记许可证未知与假冒开源的非OSI许可证、推荐动作——遵守、替换、移除、寻求法律审、寻求商业许可。

## 指令

1. **加载 `~/.claude/plugins/config/claude-for-legal-cn/ip-legal-cn/CLAUDE.md`。** 存在占位符时停下提示："先运行 `/ip-legal-cn:cold-start-interview`——我需要先学你执业档案（与OSS政策，如有）才能审查。" 如执业档案指向上传的OSS政策，也读——它是本团队接受/审查/禁止许可证的真相源

2. **确立范围：** 依赖清单（package.json、requirements.txt、go.mod、Gemfile、Cargo.toml、pom.xml、SBOM）、单个库或团队准备对外开源的代码。用户传路径时从文件推断；否则问

3. **确立部署模型** 在分类义务前——SaaS、分发二进制、仅内部或嵌入。**同一依赖清单按此触发不同义务**

4. **走下方工作流。** 特别：
   - **读实际许可证文本**，非仅元数据——LICENSE文件可能错，包元数据可能过时
   - 分类每包为宽松/弱copyleft/强copyleft/公共领域/非OSI/未知
   - 标记许可证未知为"需审"，非默认宽松
   - 标记假冒开源的非OSI许可证（SSPL、BUSL、Commons Clause、Elastic License、fair-source）——**这些非开源**
   - 对外代码时，检查所选对外许可证与每个嵌入依赖兼容

5. **按下方模板输出备忘录**——工作成果头部先、底线、备忘录顶部标记、按严重性逐包块、法域说明、对外检查（如适用）、审批路由

6. **尊重决策立场。** copyleft触发分析取决于争议问题（AGPL"通过网络交互"、GPL-3.0"传递"、LGPL链接范围）时，标记律师审并浮现两面因素。**任何标为强copyleft或许可证未知在依赖发布或代码发布前去律师**

```
/ip-legal-cn:oss-review redis
/ip-legal-cn:oss-review ~/code/我的项目  # 代码库根——扫所有manifest
```

## 中国开源许可证效力概述

**中国法承认开源许可证的合同效力，但司法实践发展中：**

- **法律基础：** 民法典合同编（第470条以下）+著作权法+计算机软件保护条例
- **判例发展：**
  - **「数字天堂」案（北京知识产权法院，2018）：** **中国司法首次认可GPL v2的效力**——涉GPL v2条款"如未按GPL v2条款分发，则不能获得任何权利"的分析
  - **「玩加案」（北京互联网法院，2019）：** **进一步确认开源许可证效力**——GPL违约触发著作权侵权而非仅违约责任
  - **「不小心案」（广州互联网法院）：** 开源许可证违反的责任分析
- **合规实务趋势：** 中国头部企业（华为、阿里、腾讯、字节等）设立开源合规团队；金融、政务系统对开源合规审查加强

**中国实务与美国的关键差异：**
- **无美国意义上的"open source license as covenant vs. license"辩论**——中国按合同法+著作权法综合判断
- **AGPL/SSPL等在中国的效力尚未有明确判例**——但按合同自由与著作权法权利限制原则，条款效力应予承认
- **中国信创、政务、金融行业**对开源使用有额外合规要求

## 目的

告诉用户依赖树中什么许可证、按代码将如何部署那些许可证触发什么义务、对每一个做什么。**输出是律师（或有律师访问的工程师）可行动的备忘录**——遵守、替换、移除、寻求法律审、寻求商业许可

**这是初次分类。** copyleft分析取决于部署模型、链接程度、法域，有时取决于**中国法尚未测试的**法律问题（特别AGPL"通过网络交互"、GPL-3.0专利条款、混合许可证兼容性）。**任何分类为强copyleft或许可证未知的，律师在依赖发布或代码发布前评估**。技能报告发现；律师决定做什么

## 先决条件：加载执业档案

**扫描依赖前**读 `~/.claude/plugins/config/claude-for-legal-cn/ip-legal-cn/CLAUDE.md`。若缺失或含占位符停下跑 `/ip-legal-cn:cold-start-interview`。执业档案告诉你：

- copyleft义务升级路由

## 工作流

### 第1步：范围是什么？

问（或从用户提供推断）：

> 我们审查什么？
>
> 1. **依赖清单** —— `package.json`、`requirements.txt`、`go.mod`、`Gemfile`、`Cargo.toml`、`pom.xml`、SBOM（SPDX/CycloneDX）、lockfile
> 2. **单个库** —— 你考虑加的具体包
> 3. **我们自己代码** —— 我们计划对外开源需检查嵌入什么

分析路径不同：

- 依赖清单 → 分类每条目，卷起义务
- 单个库 → 分类一个包并走其传递依赖如可用
- 对外代码 → 检查嵌入什么（直接与传递）、检查所选对外许可证是否兼容所有嵌入许可证、检查LICENSE/NOTICE文件正确

### 第2步：部署模型是什么？

**这是许可证清单后单个最重要输入**——**同一库按软件如何交付携带不同义务**。问：

> 这如何部署？
>
> 1. **SaaS/托管服务** —— 用户通过网络访问；无东西送到用户
> 2. **分发二进制** —— 我们把编译代码送到用户（桌面app、移动app、本地部署服务器、CLI工具）
> 3. **仅内部** —— 仅公司内部使用，不分发到外部
> 4. **嵌入/固件** —— 送在硬件中或作为封闭系统固件
> 5. **中国信创/政务/金融系统** —— 中国信创目录、政务云、金融业IT系统——有特殊合规要求

| 部署 | 重要许可证 |
|---|---|
| SaaS | **AGPL（网络触发）**、UI中宽松归属、若作为竞争服务重新利用则SSPL/BUSL/Elastic |
| 分发二进制 | **GPL、LGPL、MPL、EPL**（都在分发时触发）、宽松归属 |
| 仅内部 | 大多数copyleft**不触发**——无分发。宽松归属仍好卫生。**AGPL仍触发如公司外用户通过网络交互** |
| 嵌入/固件 | **GPL特别难合规**（源码披露+可重现构建+某些情况下的安装信息）。**在发布前计划，非之后** |
| 中国信创/政务 | **信创目录合规**+可能要求源码交付+**中国主权云与安全审查** |

**在输出备忘录中标记部署模型**——同依赖清单审对"SaaS"vs"分发二进制"产生不同义务

### 第3步：分类每个依赖

对每个包，确定许可证。**读实际许可证文本，非仅元数据**——LICENSE文件可能错（文件说MIT但头部说GPL；README声Apache但无许可证文件），包管理器元数据可能过时

分类到：

| 桶 | 示例 | 关键义务 |
|---|---|---|
| **宽松** | MIT、BSD-2-Clause、BSD-3-Clause、Apache-2.0、ISC、Zlib、Unlicense | 归属、保留许可证文本，Apache-2.0加专利授予+NOTICE要求 |
| **弱copyleft** | LGPL-2.1、LGPL-3.0、MPL-2.0、EPL-1.0、EPL-2.0、CDDL | 文件级或库级源码披露；链接规则各异 |
| **强copyleft** | GPL-2.0、GPL-3.0、AGPL-3.0、OSL、EUPL（按版本） | 广泛源码披露；**AGPL延伸到网络使用** |
| **公共领域/献身** | CC0、Unlicense、WTFPL | 通常无义务，但**中国法域公共领域献身效力有争议**（大陆法系传统对不可放弃著作权谨慎——参考著作权法第10条人身权不可转让） |
| **非OSI源码可用** | SSPL、BUSL、Commons Clause、Elastic License、Confluent Community、fair-source系 | **非开源**——限制商业使用、竞争服务使用或两者。**读具体许可证**。**中国合规特别注意：某些云服务限制条款可能影响中国云服务商** |
| **其他/自定义/未知** | 供应商特定、专有、缺许可证文件、文件与头部许可证冲突 | **停下——默认不视为宽松** |

标记：

- **双许可证包** —— 我们用哪个许可证？选择可能变义务
- **弃用包** —— 包不再维护；有支持替换吗？
- **自身树中有copyleft依赖的包** —— 顶层许可证宽松但传递依赖copyleft
- **近期改变许可证的包** —— Redis、MongoDB、Elastic、HashiCorp——确保pin的版本在你以为的许可证下
- **中国厂商开源项目：** 阿里、腾讯、字节跳动、华为等的开源项目——多数为宽松（Apache-2.0）但注意某些为**Mulan PSL v2**（中国**木兰宽松许可证v2**——由中国开放原子开源基金会+ISO/IEC认可）——**Mulan PSL v2兼容Apache-2.0，是有效中国本土宽松许可证**

### 第4步：映射义务到部署模型

对每个分类依赖，说明部署模型触发什么：

```markdown
### [包@版本] —— [许可证]

**分类：** [宽松 / 弱copyleft / 强copyleft / 公共领域 / 非OSI / 未知]

**我们部署（[SaaS / 二进制 / 内部 / 嵌入]）的义务：**

- [ ] [具体义务——如"随app的NOTICES文件中含归属"]
- [ ] [如"若我们修改并分发，公开我们修改的源码"]
- [ ] [如"AGPL网络触发——如用户通过网络访问我们修改的版本，需向其提供源码"]
- [ ] [中国信创/政务系统合规要求]

**风险：** 🔴 关键 | 🟠 高 | 🟡 中 | 🟢 低

**推荐：** [遵守义务 | 用[替代]替换 | 移除 | 发布前律师审 | 从[厂商]寻求商业许可]
```

> **copyleft依赖如何消费？** 链接关系决定copyleft是否实际触发。问或确定：
> - **静态链接/一起编译：** 作品组合为一个二进制。copyleft触发强信号（LGPL"基于库的作品"、GPL演绎作品）
> - **动态链接/共享库：** 作品在运行时保持可分离。LGPL明确许可此（"用库的作品"）。GPL立场有争议（FSF说演绎，其他不同意）
> - **头文件包含/内联函数：** 可创建演绎作品，取决于包含多少
> - **子进程/IPC：** 通过明定义接口通信的独立进程。通常不演绎
> - **网络API调用：** 大多数许可证不。**AGPL：** 网络交互条款意味着通过网络提供软件是分发。**微服务架构中API后的AGPL组件仍触发**
> - **文件范围copyleft（MPL）：** 仅修改文件带copyleft，非整个作品。检查是否修改任何copyleft文件

> **严重性评级取决于此。** "LGPL——弱copyleft，链接规则各异"无链接分析是让工程师被起诉的答案。**专有产品中静态链接LGPL是🔴关键**。**动态链接LGPL是🟢低**。同许可证，相反评级

**严重性校准：**

| 级别 | 意义 |
|---|---|
| 🔴 关键 | 强copyleft在触发它的部署（如GPL在分发二进制、AGPL在SaaS）。业务模式实际冲突的非OSI许可证（如SSPL在我们构建托管服务时）。**中国信创系统对GPL/AGPL的态度**（部分领域要求源码交付）。**许可证无法确定且包承重** |
| 🟠 高 | 团队未准备的弱copyleft义务（文件级披露、NOTICE要求）。所选许可证模糊的双许可证。许可证文件说一件事，头部说另一件 |
| 🟡 中 | 尚未接入构建的归属要求的宽松（缺NOTICES文件、分发中缺LICENSE）。可能或可能不触发的位置的传递copyleft，按库如何消费 |
| 🟢 低 | 义务已满足的宽松。不触发它的部署模型中的copyleft（如仅内部使用的GPL库，无重分发） |

### 第5步：标记失败模式

在顶部备忘录部分调出以下任一：

- **许可证未知** —— 分类为"需审"，非宽松。**未分类依赖应停出货决策，非漏过**
- **许可证文件与文件头部冲突** —— 读两者并报告冲突
- **不兼容组合** —— GPL-2.0-only+Apache-2.0历史上已知不兼容；仔细检查MPL/EPL/GPL组合
- **假冒开源的非OSI许可证** —— **SSPL、BUSL、Commons Clause、Elastic License、Confluent Community**。**读许可证；不依赖GitHub"open source"徽章**
- **许可证变更** —— 之前版本宽松而当前版本源码可用时，pin重要
- **中国合规特别标记：**
  - **数据主权**：某些开源软件默认将数据/日志上报到境外服务器——可能违反数据出境规则（个保法第38条+数据出境安全评估办法）
  - **加密算法**：使用了境外加密算法而非中国SM系列（SM2/SM3/SM4）可能不符合密码法+商用密码管理条例要求（金融、政务系统必需）
  - **信创目录**：若要进入国产信创目录，可能有软件供应链本土化要求

### 第6步：对外检查（如审查自己代码前开源）

用户准备对外开源代码时：

- 确认所选对外许可证与每个嵌入依赖许可证兼容（如你不能用MIT发布若嵌入GPL代码——组合作品必须GPL）
- 确认LICENSE文件存在且正确
- 确认NOTICE文件存在且列必需归属（Apache-2.0与其他）
- 确认第三方许可证文本按需要打包
- 确认无专有或机密代码、无客户数据、无嵌入凭据在代码库历史
- 确认商标与品牌政策对任何项目名（与著作权许可证分开）
- **中国对外开源特别检查：**
  - **是否走公司对外开源审批流程？**（大厂如阿里/腾讯/字节都有内部对外开源审批）
  - **是否考虑木兰PSL v2作为对外许可证？**（中国本土宽松许可证，Apache-2.0兼容，中国开放原子开源基金会推荐用于中国项目）
  - **是否发布到中国开源社区？**（Gitee、CSDN、GitCode、OpenAtom等）
  - **数据/日志/加密相关项目：** 检查是否符合密码法+数据安全法要求

```markdown
## 法域说明

**中国开源许可证效力：** GPL v2效力已由「数字天堂」案（北京知产法院2018）+「玩加案」（北京互联网法院2019）等判决确认。**AGPL/SSPL在中国司法效力尚无明确判例但按合同自由与著作权法原则应予承认**。**GPL-3.0专利条款+LGPL链接范围**——中国法解释仍在发展。**公共领域献身**：中国法（人身权不可转让+著作权法第22条）对完全放弃承认较窄——CC0/Unlicense实际按最广许可对待

**中国信创/主权/合规：** 若产品用于中国信创目录、政务云、金融系统，可能有本土化要求（本地厂商+源码交付+境内数据）
```
