# 缺口浮现（Gap Surfacer）

> 责任人通知：默认开启。若要豁免某个责任人，把 `owner_slack` 留空。

## 每次发送前必须逐条确认 —— 无例外

在通过企业微信 / 钉钉 / 飞书（下称「IM」）发出任何一条消息之前（新任务分派、逾期提醒、批量通知、状态报告），必须：

1. 展示准备发送的**具体内容**与**收件人**：「我将向 [N] 人发送以下消息：[预览]。」
2. 等待用户明确回复「是」。
3. 若消息包含法条引文、截止日、合规结论，追加：「⚠️ 消息中的引文尚未逐条核验 —— 我不会在发送前对当前法规数据库进行核验。是否加一行『使用前请核验』？」
4. 不确认，绝不发送。不管是不是节奏任务、不管是不是批处理、不管昨天发过没有。

「无确认自动发送」是本插件中**最不可逆**的动作 —— 把插件页脚说「可能有误」的内容，发给收件人（他们又没法自行核验）。这种组合不能跳过审查。

## 事项上下文

**事项上下文。** 读执业级 CLAUDE.md 中 `## 事项工作区` 一节。若 `启用` 为 `✗`（公司法务默认状态），跳过本段 —— 技能使用执业级上下文，事项机制不显现。若已启用且当前无活动事项，问：「本次工作属于哪个事项？运行 `/regulatory-legal-cn:matter-workspace switch <slug>`，或回答 `执业级`。」加载活动事项的 `matter.md` 以获得事项级上下文与偏差。输出写入事项目录 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/matters/<matter-slug>/`。除非 `跨事项上下文` 为 `on`，绝不读取其他事项的文件。

## 目的

缺口被发现，然后被遗忘。本技能把缺口跟到关闭为止，并向该关闭它的人发通知。

## 追踪表

存放于 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/gap-tracker.yaml`：

> **关于 comment-tracker.yaml：** `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/comment-tracker.yaml` 是同目录的另一个文件，归 comments 技能所有。由 reg-feed-watcher（自动登记草案）和 comments 技能（登记决策）写入。本技能不读取也不交叉引用它。若修改 comment-tracker 字段结构，两个真正的使用方都要同步更新。

```yaml
gaps:
  - id: GAP-001
    requirement: "[新规要求什么]"
    regulation: "[名称 + 文号 —— 例如「个人信息保护法第 21 条」或「网信办 [2024] 第 X 号」]"
    policy_affected: "[企业内部制度名称 或 '需新建制度']"
    gap_type: "partial"  # none | partial | full | new-policy | watch | comment-decision
    owner: "[取自制度库索引 —— 责任部门或责任人]"
    owner_slack: "[企业微信 / 钉钉 / 飞书用户 ID 或手机号，若已知]"
    opened: 2026-03-01
    due: 2026-06-01  # 法规生效日、企业内部截止日、或征求意见截止日
    status_verified: true  # false 表示上游 policy-diff 未能核实该法规现行有效性；未核实项永远不进入「🔴 逾期」桶
    status: "open"  # open | in-progress | closed | risk-accepted
    notified: false  # 分派通知发出后置为 true
    resolution: ""  # 关闭时填写
```

**未核实法规上不得升为「逾期」。** 「🔴 逾期」的语义是「已经错过了具有约束力的截止日」。若法规现行有效性未核实（policy-diff 设置了 `status_verified: false`，或该法规已发布超过 12 个月 / 已过施行日但未确认当前状态），截止日可能不具有约束力。此时用 🟡「需复核」并注明：「若该法规按公布内容现行有效，则已逾期 [N] 天。上升前先核实法规状态。」这类项目路由到 `watch` 桶，不进入活动的逾期 / 快到期桶；`watch` 桶的重访节奏强制在再次浮现为合规缺口前必须先做法规状态核实。

**`gap_type` 语义：**

| 值 | 含义 | 提醒节奏 |
|---|---|---|
| `none` | 制度已覆盖该要求。仅做审计留痕。应为少数 —— 若绝大多数条目都是 `none`，很可能是把 diff 跑在了错误的制度上。 | 无自动提醒。 |
| `partial` | 制度涉及该主题，但未完全覆盖新要求。需要局部修订。 | 到期前 30 日提醒。 |
| `full` | 制度与新要求相矛盾，或完全未涵盖。需要重写或新增章节。 | 到期前 30 日提醒。 |
| `new-policy` | 无现行制度覆盖此项。需要新起草制度。 | 到期前 30 日提醒。 |
| `watch` | 前瞻性条目 —— 未定稿的征求意见稿 / 立法建议。今日无合规义务；制度调整等待正式定稿。`due:` 是重访日（通常为草案预计发布日或一年后），不是合规截止日。 | 无自动提醒；正式稿发布或重访日到达时重新评估。 |
| `comment-decision` | 「是否提交意见」尚在决策中 —— 立法草案 / 部委规章草案的意见提交决策。`due:` 为意见截止日。 | 到期前 21 日提醒（比合规缺口更早，因为起草窗口更短）。 |

`watch` 与 `comment-decision` 不是合规缺口 —— 而是 reg-feed-watcher 与 comments 技能产出的**前瞻性追踪工件**。在状态报告中单独一栏浮现，让在早上七点看报告的律师一眼分得清「监管发现之前该修好的」和「先盯着的」。

## 模式

### 模式 1：从 policy-diff 摄入

policy-diff 发现缺口时，追加到 gap-tracker.yaml。去重 —— 相同要求 + 相同制度 = 同一条缺口，不重复计数。

**摄入后，通知责任人：**

若 IM MCP 可用且 `owner_slack` 已配置：

向缺口责任人发送 IM DM —— **但必须先走本文件顶部的「每次发送前必须逐条确认」流程**。向用户预览消息，等待明确确认，再发送：

```
📋 有新的合规缺口分派给你

缺口：[GAP-ID] —— [要求，一句话]
法规依据：[名称 + 链接]
影响制度：[制度名称 或「需新建制度」]
截止日：[法规生效日 或 内部截止日]

查看完整缺口跟踪表：/regulatory-legal-cn:gaps
```

发送后将追踪表中该条目的 `notified` 置为 `true`。

若 IM MCP 未连接：在状态报告中注明「责任人通知未发送」，标记为人工跟进。

## 档案缺失时的回退

本技能从 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` 读取缺口响应责任人与升级路径。当所需值为空或仍为 `[待填写]`：

- **缺口初判人未设：** 分派留空，输出追加：「`## 缺口整改流程` 中未设置初判人。请通过 `/regulatory-legal-cn:cold-start-interview --redo` 或直接编辑 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` 指派一位，以便新缺口能自动路由。」
- **新摄入缺口的责任人未知（制度库中该制度无负责人）：** 该缺口 `owner: [待分派]`，输出追加：「[N] 条缺口摄入时无负责人，因为制度库未标注影响制度的负责人。请在制度库的『负责人』列填入。」
- **重大缺口逾期但升级路径未设：** 仍按逾期报告，输出追加：「未设置重大逾期缺口的升级路径。请通过 `/regulatory-legal-cn:cold-start-interview --redo` 或直接编辑 CLAUDE.md 设置。」

值已填写时不要提配置。

**到期日提醒逻辑（状态报告与定时 agent 运行时触发）：**

提醒节奏是 `gap_type` 的函数 —— 合规缺口提前 30 日预警，意见决策项提前 21 日（更紧，因为起草窗口更短），观察项无自动提醒（正式稿发布时再评估）。

对每条 `open` 或 `in-progress` 状态的缺口：

- `partial`、`full`、`new-policy`、`none`：截止日在 30 日内且过去 7 日内未发送过提醒 —— **预览** 一条 IM DM（标题「⏰ 提醒：合规缺口将在 [N] 日后到期」），等待逐条确认再发送。
- `comment-decision`：意见截止日在 21 日内且过去 7 日内未发送过提醒 —— **预览** 一条 IM DM（标题「💬 意见决策截止日 [N] 日后到期」），等待逐条确认再发送。
- `watch`：无自动提醒。追踪表复核时或该条法规的正式稿发布时再评估。
- 若合规缺口截止日已过：在报告中标为逾期，**预览** 一条 IM DM，等待逐条确认再发送。
- 若 `comment-decision` 项截止日已过而意见未提交：标为逾期，**预览** 一条 IM DM（等待逐条确认），并要求责任人将状态更新为 `risk-accepted`（主动决定不提交）或 `closed`（意见已提交）并注明。
- 在追踪表中记录提醒时间戳，避免重复打扰。
- 批量提醒也必须逐条确认。预览「即将向 12 人发送 DM」并等待「是」算数；沉默批量发送不算。

### 涉及合规确认的动作前置门槛

**在把一条缺口关闭为「已整改」之前，或在生成任何证明公司已合规某条监管要求的输出（内部合规声明、董事会报告、审计答复、监管答复）之前：** 读取 `~/.claude/plugins/config/claude-for-legal-cn/regulatory-legal-cn/CLAUDE.md` 中 `## 谁在用` 一节。若角色是**非律师**：

> 证明合规 —— 或将缺口关闭为「已整改」—— 有法律后果。日后一旦被证明不实，该证明会被援引不利于公司；提早关闭则会掩盖未整改的暴露。是否已经与律师确认过？若是，继续。若否，我准备一份对话提纲：
>
> - 缺口（要求、法规来源、policy-diff 的发现）
> - 拟采取的整改**覆盖到什么、没覆盖到什么**
> - 是否还有残余缺口或模糊之处
> - 未解决的问题
> - 潜在风险（过宽的合规证明、遗留义务未处理、与既往公开立场不一致）
> - 需要向律师确认的问题（是否真的算已闭环、是否应作风险接受并写明理由、是否需要外部律师会签）
>
> 若尚未有稳定律师联系人：可联系公司常年法律顾问、公司所在地律师协会转介服务、地方司法局公共法律服务中心。

未取得明确「继续」，不得关闭缺口，也不得产出合规证明类文书。状态报告与追踪视图不受此门槛限制。

### 模式 3：关闭一条缺口

```
/regulatory-legal-cn:gaps --close GAP-001
整改结论：「制度 v2.3 已修订并经 [日期] 审批通过」
```

状态置为 closed，记录整改结论与关闭日期。

### 模式 4：风险接受一条缺口

有时候答案是「我们不整改」。这是一个合法决策 —— 但**必须留痕**。

```
/regulatory-legal-cn:gaps --accept GAP-002
理由：「该要求仅适用于 [某条件]，本公司不满足该条件。触发 [某事件] 时再评估。」
接受人：[有权决定的姓名 / 职务]
```

状态 → risk-accepted。保留在追踪表中（不删除）但从活跃缺口报告中掉出。

## 与 reg-change-monitor agent 的协同

Agent 的摘要包含缺口数与最久开放缺口天数。若有任何项跨过截止日，置于摘要顶部。Agent 还负责执行到期日提醒检查并发出待发的 IM 通知（同样受逐条确认约束）。

## 以下一步决策树收尾

按 CLAUDE.md `## 输出` 的规范收尾。把默认五个分支（起草 X、升级、补事实、观察等待、其他）调整为本次输出实际产生的内容。决策树是输出 —— 律师做选择。

若追踪表浮现的开放缺口超过约 10 条，或用户主动要求：提供仪表盘视图（见 CLAUDE.md `## 输出 → 数据密集型输出的仪表盘选项`）。把仪表盘做成对本次输出有意义的形状 —— 按严重度的计数、按截止日的时间线、按责任人 / 状态 / 最后触发日排序的表格。

## 本技能不做的事

- 不自行关闭缺口。关闭必须有整改结论 + 结论所描述的**人工动作**。
- 若 IM MCP 未配置，不发通知。回退到在状态报告中标注人工跟进。
- 每 7 日一条缺口最多发一条提醒。**唠叨一次，不常态化打扰。**
