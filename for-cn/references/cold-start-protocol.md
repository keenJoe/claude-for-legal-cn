# 冷启动访谈通用协议（cold-start 骨架）

本文是 for-cn 全部 12 个插件 cold-start-interview 技能的**共享骨架**。每个插件在其上叠加自己的 playbook 问题清单（见各插件 agent 任务书中的「Playbook 访谈问题」）。写技能时把它们整合成一个完整 SKILL.md，不要只引用本文件。

## 一、frontmatter 模式

```yaml
---
name: cold-start-interview
description: >
  执行冷启动访谈，了解你的<领域>实践并写入执业档案：
  `~/.claude/plugins/config/claude-for-legal-cn/<插件名>-cn/CLAUDE.md`。
  首次使用插件、配置文件缺失或仍有占位符、或用户说「配置插件」「初始化」「教我使用」时使用。
  这是新安装后应运行的第一个技能。
argument-hint: "[--redo 重新访谈] [--check-integrations 只检查集成] [--xxx 领域专项]"
---
```

注意：config 路径用 `claude-for-legal-cn`（市场名），插件目录用 `<插件名>-cn`。

## 二、检查当前状态

1. 读 `~/.claude/plugins/config/claude-for-legal-cn/<插件名>-cn/CLAUDE.md`
2. 含 `[待填写]`/`[PENDING]` → 全新访谈或续接：含 `<!-- SETUP PAUSED AT: -->` → 问候并续接；含 `[待填写]` 但无暂停注释 → 从占位符处开始或重来
3. 已填好 → 问：「看起来已配置完成。要重新访谈吗？会先展示差异再覆盖。」

## 三、快路径 / 全量路径

- **快路径**：只问「谁在用」+「连接了什么」+ 当前立场（如有侧别）。其余写 `[DEFAULT]`。结尾：「已配置完成。已为 playbook 立场、审批阈值、文风使用合理默认值。当某个技能输出感觉不对时，通常是应该调整的默认值——它会提示你调哪个。随时运行 `/<插件名>-cn:cold-start-interview --full` 重做，或 `--redo <章节>` 只重做一部分。」
- **全量路径**：以下完整流程。

## 四、开场前必做

1. **fork 前导**：3-4 行，说明本插件适用人群 +「2 分钟/15 分钟」提示 + 询问快或全量（等回答）。
2. **安装范围检查**：若工作目录在某个项目内（非用户主目录），提示一次项目级安装限制。
3. **连接检查**（仅在 `--check-integrations` 或用户要求时执行完整的）：逐个 probe，只有真实调用成功才标 ✓；配置未验证标 ⚪ 并给一行确认方法；**绝不因 .mcp.json 里声明了就报 ✓**。

## 五、访谈内容（快路径共用）

### 谁在用
1. 律师或法律专业人员（含法务、合规、律师助理）
2. 有律师可咨询的非律师（业务负责人、销售、HR）
3. 无常规律师渠道的非律师

选 2/3 时说明一次（不要每次输出都重复）：
- 输出定位为「供律师审核的研究材料」而非结论
- 在涉及法律后果的步骤前暂停（签署、发函、发送给相对方），问是否已与律师确认，并生成一页纸供律师快速判断
- 选 3 时补充：可联系当地律师协会、法律援助机构、公共法律服务中心

### 连接了什么
按插件实际需要的集成逐个检查：合同管理系统（如法大大、e签宝、飞书审批）、法规检索（北大法宝/威科先行/国家法律法规数据库）、企业征信（企查查/天眼查/国家企业信用信息公示系统）、办公（企业微信/钉钉/飞书/WPS）、签署平台。格式：

```
- ✓ [集成] —— 已验证可用
- ⚪ [集成] —— 已配置未验证，打开 MCP 设置确认
- ✗ [集成] —— 未找到。[功能] 将回退到[手动方式]。[如何连接]
```

「不需要全部接入。核心功能仅靠文件访问也能用。」

### 执业环境
- 律所（个人/团队规模） → 询问协作与外部律师咨询触发点
- 公司法务部（中大型） → 询问审批链、合规负责人、业务接口人
- 政府/高校/法律诊所 → 询问监督结构与限制
- 其他：让用户用自己的话说，不要套模板

### 公司概况（写共享执业档案 profiles 可被其它插件读取，节省重复提问）
- 公司主体全称 + 统一社会信用代码（与营业执照一致）
- 主营业务、行业、规模
- 注册地、主要经营地（决定地方监管、法院管辖、数据出境备案受理机关）
- 司法管辖足迹（是否有境外主体；决定跨法域识别触发）

### 当前痛点
- 什么会让你头疼？瓶颈在哪（检索、审查、起草、审批、期限）？

## 六、客观事实核验

用户答的条文号、金额、截止日等，若有条件核验先核验再写入档案；无法核验的标 `[待核验]`。错误事实写入 CLAUDE.md 会传播到所有输出。

```

*冷启动访谈于 [日期] 生成。直接编辑本文件 —— 插件内每个技能执行前都会读取它。
若某处写错了，改这里就等于全改。*

---
## 我们是谁
...
---
## 谁在用
**角色：** [律师/法律专业人员 | 有律师可咨询的非律师 | 无律师渠道的非律师]
**律师联系人：** [姓名/团队/外部律所/N/A]
---
## 可用集成
| 集成 | 状态 | 未接入时的回退 |
...
---
## Playbook

### <领域核心检查点>（逐项：标准立场/可接受退让/绝不接受/从样本合同得到的实际立场）
```

## 八、写完之后

1. 展示摘要 +「哪里不对？」
2. 推荐尝试：「要不要拿一份真实<文档类型>试试？看看我刚学的 playbook 用起来怎么样。」
3. 研究工具提示：「开始第一次审查前先接一个法规检索工具。没接之前，我会把所有引用标注为未核验；接了之后我会在提交前对当前数据库核验。」
4. 变更性说明：「档案是普通文本文件，可直接编辑。任何回答都可以改：直接编辑文件 / `--redo` 全面重访 / `--check-integrations` 只查连接。」
5. 学习性说明：「档案会随着使用变好。技能输出不对时通常是某个立场该调了；若同一偏差多次批准，监控 agent 会提议把 playbook 更新为实际做法。」

## 九、失败模式

- 不写 YAML 样式的「配置文件」—— 档案是可读散文 + 表格
- 不跳过样本文件 —— 访谈提供「他们认为的 playbook」，文件提供「实际生效的 playbook」，两者都重要
- 不写通用 playbook —— 用户答「合理市场条款」时要追问具体数字
- 不承诺本插件没有的技能能力
- 不在每次会话都跑访谈 —— 先检查配置文件
