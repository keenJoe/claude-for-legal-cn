# /matter-close

1. 按下方工作流。
2. 确认 slug 与当前状态。
3. 捕捉结果：结案类型（调解结案、和解、撤诉、一审判决胜、一审判决败、上诉后二审胜/败、再审、执行终结、合并进另一案）、结案日、最终敞口/成本、经验教训。
4. 更新 `_log.yaml`：`status: 已结案`，追加 `closed: YYYY-MM-DD` 和 `outcome:` 字段。
5. 追加最终条目到 `~/.claude/plugins/config/claude-for-legal-cn/litigation-legal-cn/matters/[slug]/history.md`。
6. 案件保留在 `_log.yaml` 和文件夹中 —— **不删除**。`/portfolio-status` 默认过滤已结案。

# 案件结案

## 目的

案件会结束。结果是组合视图产生的最有价值的数据 —— 它校准未来案件的风险框架。结构化捕捉结果比"归档"更重要。

## 加载上下文

- `~/.claude/plugins/config/claude-for-legal-cn/litigation-legal-cn/matters/_log.yaml` —— 找到行
- `~/.claude/plugins/config/claude-for-legal-cn/litigation-legal-cn/matters/[slug]/matter.md` —— 立案上下文（参照）
- `~/.claude/plugins/config/claude-for-legal-cn/litigation-legal-cn/matters/[slug]/history.md` —— 追加目标

**利益冲突门槛 —— 不可绕过。** 结案前检查 `_log.yaml` 是否有此 slug。若不在：

> "在案件台账中没找到 [slug]。没法结案 —— 要么 slug 写错，要么这个案件从未通过 `/litigation-legal-cn:matter-intake` 立案。先核对 slug；若确实没立案过，就没有行可更新、没有文件夹可结案。"

## 输入

slug（必需）。

## 结案

### 1. 结案类型

- `调解结案` —— 法院主持下达成调解协议（民诉法第 96 条起）；含调解金额、结构性条款
- `庭外和解` —— 双方达成和解协议，撤诉或不再主张；金额、结构性条款
- `撤诉` —— 主动撤诉（民诉法第 154 条相关）或按撤诉处理；理由与后果
- `一审判决支持我方` —— 何种程度支持，对方是否上诉
- `一审判决不支持我方` —— 我方是否上诉、上诉理由
- `二审改判/维持` —— 结果、执行时间
- `再审` —— 提出/被提出，结果
- `执行终结` —— 执行完毕、终结本次执行、终结执行；实际到账金额
- `合并进另一案` —— 提供合并后 slug
- `其他` —— 补充说明

### 2. 结案日

案件实际结束的日期（调解协议签署、判决生效、和解协议签署、撤诉裁定送达、执行终结裁定）。

**判决生效日的判断：** 一审判决在上诉期届满且未上诉 → 生效；一审后上诉 → 二审裁判送达生效；再审 → 按再审文书。

### 3. 最终敞口/成本

- 实际支出：调解/判决/和解金额 + 律师费 + 诉讼费 + 保全费 + 鉴定费 + 其他
- vs. 立案时预估的敞口区间（我们判断对了吗？）
- 准备金准确度（若已提）：账面 vs. 实际
- 已收回金额（原告方）—— 强制执行的实际回收率

### 4. 经验教训

两三句话。哪里做对了？哪里判断失误？立案时应当更早识别的信号？

这是未来的律师会重读的部分。诚实点。「误判可能性 —— 对方委托的律所比预期更强硬」比「有利结案」更有价值。

### 5. 关联文书

调解书、判决书、执行终结裁定、和解协议 —— 有路径的话记录。非强制。

## 写入

**结案前的关卡（有法律后果 —— 案件被归档、活跃追踪结束）：** 读 `## 谁在用这份档案`。若审查人是非律师：

> 结案有法律后果 —— 它结束活跃追踪，可能影响任何相关的证据保全（视情况另跑 `/legal-hold --release`），并确立公司依据的最终记录。你与律师确认过了吗？确认过就继续。若还没：这里是一页纸供沟通用：
>
> [生成一页摘要：案件、结案类型和条款、最终敞口 vs 立案预估、准备金准确度、是否有关联案件或未决上诉、过早结案可能出的问题、要问律师什么]
>
> 找不到律师？中国实务：本地律协的公益法律服务、法律援助中心、公共法律服务热线 12348 是快速起点。

未获明确 yes 前，不写入结案字段、不追加结案条目。

### 更新 `_log.yaml`

```yaml
status: 已结案
closed: [YYYY-MM-DD]
outcome: [结案类型]
final_cost: [金额]
recovery: [已回收金额 —— 原告方]
last_updated: [今日]   # 结案是最后一次触碰，记录
```

保留所有既有字段。**不删除行**。

### 追加最终条目到 `history.md`

```markdown
## [YYYY-MM-DD] —— 案件结案：[结案类型]

**结果：** [叙事 —— 发生了什么、条款如何]
**最终成本：** [金额 + 结构性条款]
**vs. 立案预估：** [对比 matter.md 预估区间]
**准备金准确度：** [如适用]
**执行回收（原告方）：** [实际到账 / 应付未付原因]

**经验教训：**
[2-3 句 —— 诚实的复盘]

**关联文书：** [调解书 / 判决书 / 执行终结裁定 / 和解协议 —— 若有]
```

### 触碰 `matter.md`

末尾追加结案块（不改动前文，前文是立案时的历史）：

```markdown
---

## 结案 [YYYY-MM-DD]

[一段结果摘要。指向 history.md 最终条目获取细节。]
```

## 确认

写入前完整展示结案条目和 yaml 变更给用户看。

## 转换决策

- 分级：**A 直接转化**。原版结构（结果 → 敞口 → 教训 → 归档）保留；实体层：结案类型换为中国诉讼实务（调解结案、庭外和解、撤诉、判决、二审、再审、执行终结、合并）；判决生效日专门说明；执行回收率作为原告方独有指标补入。

## 这个 skill 不做的事

- 删除案件。已结案的仍留在 `_log.yaml` 和磁盘上 —— 它们是组合判断的训练集。
- 重开案件。若已结案的又回来了（申请再审、新执行程序、相关案件），新建一个案件并在 matter.md 中引用旧的。
- 编造教训。用户跳过教训环节就留空，不发挥。
