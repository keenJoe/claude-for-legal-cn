# /closing-checklist

1. 读取 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/deals/[code]/closing-checklist.yaml`，按下面的模式操作。
2. 提供了状态更新 → 模式 3（更新项目）。
3. 其它情况 → 模式 4：阻塞项、关键路径、距交割天数。

---

## 事项上下文

**事项上下文。** 检查执业档案 CLAUDE.md 中的 `## 事项工作区`。若 `启用` 为 `✗`（法务用户的默认值），跳过本段其余内容——技能直接使用执业层上下文，事项机制不可见。若已启用且没有活动事项，询问：「这是哪个事项？运行 `/corporate-legal-cn:matter-workspace switch <slug>` 或说『执业层』。」加载活动事项的 `matter.md` 获取事项特有上下文与覆盖项。输出写入事项文件夹 `~/.claude/plugins/config/claude-for-legal-cn/corporate-legal-cn/matters/<matter-slug>/`。除非 `跨事项上下文` 为 `开`，绝不读取其他事项的文件。

## 用途

交割在清单全部完成时发生。每一项都完成，没有遗漏。本技能维护清单，把尽调中新浮现的项目纳入，告诉团队什么在阻塞。

## 模式

### 模式 1：从交易协议初始化

读取已签署（或接近最终版）的股权转让协议/收购协议。提取：

- 每一项交割先决条件（位置因协议而异——读实际章节标题）
- 每一项交割交付物（交割交付物清单或对应章节）
- 每一项有交割前期限的承诺事项

每项成为清单项目，并注明协议章节出处。

**填充监管/批准类项目前先研究义务。** 经营者集中申报（反垄断法）、外商投资负面清单（外商投资法）、行业专项审批（如金融、电信、数据、医疗等行业监管）有不同的机制、门槛和时限窗口，且会变化。从协议中提取每项监管条件的名称，然后研究当前生效的机制（谁申报、何时、什么会触发补充审查、等待期多长、是否需要「同意先决条件」还是「申报后等待期届满」）。引用一手来源并核实时效。不要凭记忆填时限假设。

**重大不利变化 / 重大不利影响交割条件。** 从协议中提取定义——MAC/MAE 框架是谈判出来的，不是标准的。在把某事件标记为潜在 MAC 触发前，研究协议特定表述下的法律解释——中国合同法框架下 MAE 条款的司法实践与域外法不同，法院对「重大不利变化」的认定尺度、需要与估值影响的量化关联，实践中有争议。对不确定的解释标 `[review]` 交律师判断。

**从重大合同提取同意要求** 取决于合同默认规则和每份合同中具体的禁止转让条款。逐份合同研究适用规则，不要假设统一默认。

### 模式 2：从尽调纳入（「自更新」部分）

当上游技能产出带交割前动作的发现时触发模式 2。本模式纳入的上游技能与输出类型：

- **`diligence-issue-extraction` 发现** —— 任何标记为需要交割前动作的发现（同意、股东会决议、董事会决议、监管申报、解除、托管机制、清偿函）。不止「同意」——完整清单见该技能的交接节。
- **`material-contract-schedule` 的控制权变更 / 转让项目** —— 日程构建中浮现的控制权变更条款、禁止转让条款、最惠国待遇触发。
- **`deal-team-summary` 输出** —— 高管简报汇总抽取发现，有时会浮现单个抽取备忘录机械阅读会漏掉的交割动作项（如跨多份劳动合同汇总的补偿承诺、一揽子同意包）。模式 2 读取 deal 文件夹中最新 deal-team-summary，将其中要求交割前动作、但尚未在清单上的项目对账并入。

交接 schema 覆盖全范围交割前动作，不止同意：

```yaml
handoff:
  # 必填字段
  item: "[相对方或动作，一行]"
  category: "[第三方同意 | 股东/董事会动作 | 监管申报 | 解除/终止 | 托管/留存 | 交割交付物]"
  source: "[合同名称 / 法条 / VDR 路径 + 页码]"
  blocking: true  # 除非协议有重要性限定语
  severity: "[🔴 / 🟠 / 🟡 / 🟢 — 从上游携带，见 CLAUDE.md 跨技能严重级别下限规则]"

  # 同意/第三方动作字段
  counterparty: "[如：某控股有限公司]"
  guarantor: "[如：买方母公司担保要求，或 N/A]"
  conditions: "[相对方附加的任何实质条件——如『同意生效前须提供买方母公司替代担保』]"
  notice_deadline: "[如：交割前 30 日，或具体日期]"

  # 公司动作字段
  approval_body: "[股东会 | 董事会 | 委员会 | 监管机构]"
  approval_threshold: "[如：经出席会议股东所持表决权三分之二以上通过]"
  statutory_or_charter_source: "[如：公司法第 66 条；章程第 X 条]"

  # 时限
  estimated_time_to_complete: "[如：30 天]"
  must_occur_before: "[如：交割 | 签约 | 暂停期届满]"
```

保留上游技能填写的每个字段。「需某公司同意，附替代担保条件和 30 日通知期」应在清单上以全部三个要素呈现（同意、担保人、通知），而不是坍缩成「某公司同意控制权变更」。上游给出严重级别时携带——见档案中的跨技能严重级别下限规则。

追加到清单。去重键是（相对方 + 动作类型），不是自由文本项目名——同一相对方的同意和解除是两个不同项目。去重时合并字段而不是覆盖：一个交接填了 `guarantor`，后来的交接填了 `notice_deadline`，清单行两个字段都保留。

### 模式 3：状态更新

用户（或 dataroom-watcher agent）提供状态更新。找到项目，更新状态和 last-updated。

```
/corporate-legal-cn:closing-checklist
CP-002: Acme 已回复，同意函已附，需对方会签
```

## 关键路径分析

不是所有阻塞项都同等。一个 30 天才能拿到的同意是关键路径。一个 2 天就能拿到的合规证明不是，虽然两者都阻塞。

对每个阻塞项估算完成所需时间。`(到期日 - 今天) < 估算时间` 的就是临风险项。它们排在每份状态报告最上面。

如果清单超过约 10 项，或用户任何时候要求：提供仪表板（见 CLAUDE.md `## 输出 → 数据密集输出的仪表板提供`）。为这个输出定制——按状态计数（完成/进行中/未开始/临风险）、按工作流分组的关键路径视图、可排序网格（项目、负责人、到期日、距到期天数）。

## 集成：dataroom-watcher agent

该 agent 每日检查清单，如已连接则从邮件/企业微信拉取状态更新，把「什么在阻塞」报告发到交易团队群。模式 4 是 agent 的输出。

## 后果闸门（认证交割）

**在产出「可交割 / 全部先决条件满足」的认证或交割备忘录之前：** 读档案 `## 谁在用`。若角色为**非律师**：

> 认证交割条件已满足（或产出主张此事的交割备忘录）有法律后果——它是驱动资金流转和交割后义务的信号。你是否已与律师核对？如是，继续。如否，这里有一页纸供你带去：
>
> - 全部先决条件清单及状态（完成/进行中/未开始）
> - 完成证据薄弱或缺失的任何项目
> - 对无法按时交割的项目所需的豁免或补充函
> - 未决问题（相对方同意未决、任何 MAC/补充确认风险）
> - 要问律师什么（是否可以宣布交割；哪些条件不应被绕过；什么应列入例外清单）
>
> 如需寻找律师：可联系当地律师协会或公共法律服务中心寻求推荐。

未获明确同意，不要越过此关卡产出最终「可交割」认证。状态追踪和「什么在阻塞」报告不需要过此关卡。

## 本 skill 不做的事

- 不取得同意、不提交申报、不起草文件。它追踪这些事需要发生。
- 不决定什么在阻塞——交易协议决定。本技能读协议。
- 不完成交割。它告诉你何时可以。
